## P0 · 会导致错误行为的问题

### P0-0　**[核]** `npm run build` 必然失败：`tsc` 有 1991 个错误

实测（`npx tsc --noEmit`）：

```
TOTAL = 1991
  src/we    = 231
  examples  = 1760
```

根 `tsconfig.json` 的 `include` 是 `["src", "examples"]`，且开了 `noUnusedLocals` / `noUnusedParameters` / `strict`；`package.json` 的 build 脚本是 `tsc && vite build`——tsc 非零退出后 `&&` 直接中断，**产物根本不会生成**。（`npm run dev` 正常，因为 vite dev 不做类型检查，这也是问题一直没暴露的原因。）

**分层结论（关键）**：

| 范围 | 错误数 | 性质 |
| --- | :---: | --- |
| `src/we` | 231 | **真实类型错误只有 1 个**；其余 230 个是 `TS6133 / TS6192`（未使用的导入与变量） |
| `examples` | 1760 | 混合：既有 unused，也有真实错误（如 `E_AnimationPlayType` 不含 `"count"`、`NodeObject` 未从 `organization/root` 导出） |

**`src/we` 里那唯一一个真实错误**：

```
src/we/core/gbuffers/GBuffers.ts(9,269): error TS2305:
  Module './base' has no exported member 'V_TransparentGBufferNames'.
```

即 `GBuffers.ts` 从 `gbuffers/base.ts` 导入了一个并不存在的常量。对照 `camera/TTP.ts.backup` 里同样用到 `V_TransparentGBufferNames`（`TTP.ts.backup:234`）——**这个常量应属于"透明 GBuffer"那一套设计，随 `TTP.ts` 被改名成 `.backup` 后，`base.ts` 里的定义也被删/改了，但 `GBuffers.ts` 的 import 没跟着清理**。

**修复路径（约 1～2 d，性价比最高的一条）**：

1. 修 `GBuffers.ts:9` 的那一个 import（确认 `V_TransparentGBufferNames` 是否还需要；若需要就在 `gbuffers/base.ts` 补回定义）。
2. `src/we` 的 230 个 unused：批量删未使用的 import / 变量，可用 `eslint --fix` 或 IDE 批量处理。
3. `examples` 的 1760 个：先加 `tsconfig` 的 `exclude`（或为 examples 单独放宽 `noUnusedLocals`）把门禁范围收回到 `src`，再逐步清理。
4. CI 里的 tsc 门禁**先设"错误数不增加"**，避免一上来就红、没人愿意修。

**顺带解释了一个现象**：仓库里 `TTP.ts.backup`、`mulitibl.ts.todo`、`shaderMaterial.ts.todo`、`capsuleGeometry.ts.todo` 这类后缀，**不是随手留的垃圾，而是"手工排除 `tsc` 编译"的手段**——`include: ["src"]` 只匹配 `*.ts`，改名即脱离编译。`doc/log.txt` 记录了它们还是 `.ts` 时 typedoc 报出的 253 个错误（含 `TTP.ts` 大量语法错误、`mulitibl.ts` 缺 `}`、`shaderMaterial.ts` 引用不存在的 `IV_VolumeTextureMaterial`）。**因此清理这些文件前必须确认其中逻辑是否已迁移**（透明渲染 TT 双缓冲、多 IBL、volume shader 变体、胶囊体），否则会丢失未完成的设计。

### P0-1　**[核]** GPU 资源回删删的是 Map 名，而不是资源键 → 显存泄漏

```132:148:src/we/core/organization/root.ts
    destroy(): void {
        if (this._isDestroy) return;
        this._isDestroy = true;
        if (this.resourcesGPU) {
            for (let i of this.mapList) {
                if (i.map && this.resourcesGPU.getProperty(i.map as keyof ResourceManagerOfGPU)) {
                    (this.resourcesGPU[i.map as keyof ResourceManagerOfGPU] as Map<any, any>).delete(i.map);
                }                        // ↑ 删的是 i.map（Map 的名字，如 "textureOfString"）
                else
                    this.resourcesGPU.delete(i.key, i.type);   // ← 这条分支才是对的
            }
        }
        this._destroy();
        if (this._manager) this._manager.remove(this);
    }
```

**影响**：凡是 `mapList` 中带 `map` 字段的资源，`destroy()` 时都执行 `map.delete("textureOfString")` 这类无效删除——键是字符串常量，Map 里根本不存在。**长期运行、频繁增删对象的场景会持续泄漏显存**，且因为字典条目一直存在，后续同类型资源也无法被正确回收。

**修复**：

```ts
(this.resourcesGPU[i.map as keyof ResourceManagerOfGPU] as Map<any, any>).delete(i.key);
```

**建议**：修复后加一个 debug 面板，统计 `resourcesGPU` 各 Map 的 `size`，与活跃对象数对比——这是唯一的验证手段。

### P0-2　**[核]** 输入系统的 `intercept` 优先级完全失效

```300:300:src/we/core/input/inputManager.ts
    if (j == E_InputPriority.intercept) {
```

同样写法出现在 `:314 / :334 / :351 / :366 / :378`（共 6 处）。而 `j` 是 `for` 循环的**数组下标（number）**，`E_InputPriority.intercept` 是**字符串枚举值**，二者永远不相等。

**影响**：`E_InputPriority.intercept` 这一层设计的意图是"独占消费事件、阻断后续广播"（例如 UI 打开时不应同时转动相机）。该系统**从未生效过**，所有注册在该优先级的处理器都被当普通处理器执行。表现为"拖拽 UI 时相机跟着转"这类问题。

**修复**：按层下标判断，例如 `if (j === INDEX_OF_INTERCEPT)`；或改为遍历形如 `{ level: E_InputPriority, fn }[]` 的结构。

**注意**：修复后行为会变化，需要回归所有用到 UI 交互的示例。

### P0-3　**[疑]** Pipeline 缓存 key 用字符串表达式，可能误命中

```1640:1652:src/we/core/command/DrawCommandGenerator.ts
    let cacheFlag = [md5VS, md5FS, topology, cullMode, stripIndexFormat, frontFace,
                     depthStencilFlag, multisampleFlag] ...
```

其中 `depthStencilFlag`（构造于 `:1602`）是把 depthStencil 描述拼成的**字符串表达式**（源码注释亦自承这一点）。不同的 depthStencil 参数组合可能拼出同一字符串。

**影响**：两个需要不同深度状态（如 depthWrite / depthCompare 不同）的 DrawCommand **可能错误地复用同一个 `GPURenderPipeline`**，导致深度测试行为错误——典型症状是"某些物体该遮挡的没遮挡"。

**修复**：把 `depthStencil` 与 `multisample` 的**结构化快照**（JSON 序列化带排序键，或专门的 hash 函数）纳入 cacheFlag；或改用 `resourcesGPU.get(kind)` 的嵌套 Map：先 md5VS → md5FS → topology → depthStencil hash 逐层查找。

**验证方法**：构造两个仅 depthWrite 不同的材质并在同一场景渲染，检查 `scene.resourcesGPU.pipeline.size` 是否 = 2。

### P0-5　**[疑]** 动画更新顺序：注释与实现矛盾

```803:804:src/we/core/scene/scene.ts
    // scene.ts:804 注释：动画组更新需要在动画更新之前
    animationManager.update(clock);        // :803
    animationGroupManager.update(clock);   // :804   ← 实际排在之后
```

**影响**：若注释描述的需求为真，则当前 `AnimationGroup` 拿到的是**上一帧**的各条动画状态，动画组整体会滞后一帧；在多动画权重混合（`WeightMixAnimation`）场景下可能表现为混合抖动。

**处理**：这是一个**需要动态验证**的问题。建议做 A/B：把两行互换后跑 `examples/animations/keyframe/` 与多动画混合示例对比。**在未验证前不要改**，因为也可能是注释过时。

### P0-6　**[核]** 多 primitive 的 mesh 只有最后一个生效

```1175:1175:src/we/model/gltf/gltf.ts
    this.modelRes.entity.set(Number(i), entity);   // i 是 mesh 索引，内层循环遍历 primitive
```
```41:41:src/we/model/gltf/function.ts
    let mesh = await gltf.getRes(T_ModelResKind.entity, node.mesh) as BaseEntity;
```

**影响**：`modelRes.entity` 的 key 是 mesh 索引，内层循环遍历 primitive 时不断覆盖 → 只有最后一个 primitive 留下。**多材质模型（建筑、角色）渲染不完整。**

**修复**：key 改为 `` `${i}_${j}` ``，`addNode` 为每个 primitive 各建一个 NodeObject（或引入 `MultiPrimitiveEntity`）。

### P0-7　**[核]** 局部/世界矩阵更新的条件分支不完整

`NodeObject.update()`：

```747:777:src/we/core/organization/nodeObject.ts
    update(clock) {
        super.update(clock, false, false);
        if (this.SpaceType !== physical) {                    // :750
            if (!this.DirectInWorldSpace) {                   // :752
                if (this.checkNeedUpdateWorldMatrix()) {      // :753
                    this.updateMatrixWorld();
                    this.updateWorldPosition();
                    this.updateSelfAttribute();               // :760  包围盒累加在分支里
                }
            } else {
                this.matrixWorld = this.matrix;               // :764
            }
            ...
        }
        for (let child of children) child.update(clock);       // :775
    }
```

**问题 1**：`updateSelfAttribute()`（累加 AABB 到 `scene.Box3s`）只在世界矩阵变化时才调用。`DirectInWorldSpace` 分支与 world matrix 未变时都不累加 → **`scene.Box3s` 不完整**，依赖它的 BVH / 包围盒剔除会出错。

**问题 2**：`:764` 分支没有调用 `updateSelfAttribute()`，也没有处理 worldPosition。

**修复**：把 `updateSelfAttribute()` 提到 `SpaceType` 判断之外，或给 `DirectInWorldSpace` 分支补同样的调用。

### P0-8　**[核]** `checkGPUBufferSize` / `createGPUBufferByType` 的资源创建隐患

`command/baseFunction.ts`：

- `:19-25` `checkGPUBufferSize` 补齐到 4 字节倍数的余量算法写成 `+= remainder`，正确应为 `+= (4 - remainder)`。在 size 非 4 倍数时可能仍产生非法 size。
- `:123` `createGPUBufferByType` 对**未 mappable** 的 buffer 调用了 `buffer.unmap()`，WebGPU 规范下会抛异常。

**修复**：修正余量计算；`unmap()` 只在 `mappedAtCreation` 为 true 时调用。

## P1 · 影响可维护性与正确性风险

### P1-1　`Scene` 职责发散（1391 行）
`scene/scene.ts` 同时承担：GPU 初始化、canvas 配置、26 个管理器的构造编排、包围盒、BVH、bindGroup、RPD、用户事件回调（`IV_Scene` 之外的 `IJ_Scene`，`base.ts:163-171` 还有多个 `any`）。

**建议**：拆出 4 个协作者——`GPUContext`（adapter/device/canvas/configure）、`SceneGraph`（root + Box3s + BVH）、`SceneSystems`（管理器构造与编排）、`SceneLoop`（run/update/render）。`Scene` 只做门面。

### P1-2　更新顺序硬编码，扩展点脆弱
`scene.ts:520-542`（构造顺序，注释明确要求 RenderManager 要在 entityManager 之前）、`:790-839`（update 顺序）、`renderManager.ts:562-616`（通道顺序）全部手写。

**建议**：改为声明式。给每个 Manager 标注依赖，拓扑排序后生成 update 序列：

```ts
// 示意
class SkinsManager extends ECSManager<SkinAnimation> {
  static dependencies = ['animationGroupManager', 'root'];
}
```
收益：新增子系统不会再因为"插错位置"产生难查的一帧延迟问题。

### P1-7　生产路径的 `console.log`

热点：`scene.ts:379/483/486/491/493/638/948` · `renderManager.ts:747` · `nodeObject.ts:641` · `shaderRegister.ts:365/387` · `control/OrbitCameraControl.ts:256` · `ibl/ibl.ts:192` · `pickup/pickup.ts:156/180` · `input/inputManager.ts:200`

**特别提示**：`shaderRegister.ts:365/387` 是**本该 throw 的地方被降级成了 log**——着色器解析失败时会静默继续，后续报出的错误位置会离真正的原因很远。

**建议**：引入分级 logger（`WE3D.debug / warn / error`），发布构建剔除 debug；把 `shaderRegister` 的两处改回 throw。

### P1-8　`console.warn` 掩盖缺失（glTF 层同理）
`DrawCommandGenerator.ts:626/691/833/1046/1062/1221/1237` 在多处"属性不支持"时只 warn。建议统一策略：开发期 throw，发布期 warn（由 `IV_Scene.debug` 控制）。

### P1-9　无 WebGPU 能力检测与降级页
`Scene._init()` 检测 `navigator.gpu`（`scene.ts:453`）失败时只是抛错。用户看到白屏而不知道原因。

**建议**：捕获后渲染一个提示页（"当前浏览器不支持 WebGPU，请使用 Chrome/Edge 113+ 或 Safari 26+"），并在 README 明示支持矩阵。

### P1-10　配置项文档与实现不一致（三处）

### P1-11　`Clock` 用 `Date.now()` 而非 `performance.now()`

`clock.ts:50`。`Date.now()` 精度较低且会受系统时钟调整影响（NTP 校时可能导致负 deltaTime）。

**建议**：换 `performance.now()`，并对 `deltaTime` 做上限钳制（如 100 ms），避免切后台回来后一帧巨大步进把物理/动画炸掉。
