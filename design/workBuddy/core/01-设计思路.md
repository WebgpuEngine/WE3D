## 一、设计目标与约束

从代码与注释中能还原出四条硬约束，它们解释了一切设计选择：

1. **WebGPU 原生，不为 WebGL 留退路。** 全仓直接操作 `GPUDevice / GPUBuffer / GPUTexture / GPURenderPipeline`，92 个 WGSL 手写。反向 Z、storage buffer 骨骼矩阵、多通道 GBuffer 都是按 WebGPU 语义而不是 WebGL 模拟实现的。
2. **TypeScript + 强类型意图。** 所有构造参数都定义了 `IV_xxx` 前缀的 InputValue 接口（`IV_Scene` / `IV_BaseEntity` / `IV_PBRMaterial` …），虽然实际执行中被大量 `any` 稀释了。
3. **自研，不套壳 three/Babylon。** README 自述"参考了 Babylon、three、cesium、UE"，但从内存块管理到顶点格式推断都是自己的。
4. **先跑通再优化。** 大量 `//todo` 与 `throw new Error("Method not implemented.")` 表明这是"骨架优先"的开发方式——先拉通全链路（前向/延迟/MSAA/拾取/大气），再回填细节。

**理解第 4 点很重要**：很多"未完成"不是设计缺陷，而是刻意的占位。但占位与完成的边界在代码里缺乏标注，这是当前最大的维护风险之一（见 [04](./04-问题缺陷与改进建议.md) P1-3）。

## 三、核心机制详解

### 3.1 三段式初始化（贯穿全框架的生命约定）

`RootGPU`（`organization/root.ts:18`）定义了一套严格的生命周期，**所有继承它的类（实体、材质、纹理、光源、相机……）都必须遵守**：

```
构造 new Xxx(inputValues)        只记录参数，不碰 GPU
   ↓
await obj.init(scene, parent?)   setRootENV() 拿 device/scene/resourcesGPU（:120-125）
   ↓                             然后调用子类自己的 GPU 资源创建
await obj.readyForGPU()          抽象钩子（:131），由各子类实现真正的 GPU 分配
   ↓
obj.update(clock)                每帧（:160-176）
   ↓
obj.destroy()                    幂等回收（:132-148）
```

`update()` 的骨架是模板方法模式：

```160:176:src/we/core/organization/root.ts
    update(...) {
        // 1、userDefine.update（自定义的 I_Update.update）
        // 2、updateSelf()：私有属性
        // 3、lastUpdaeTime = clock.now
        // 4、updateAtEnd 回调
    }
```

**设计意图**：把"参数 → 环境 → GPU 资源 → 每帧更新 → 回收"标准化，使任何新子系统只要实现这三段就能接入，无需关心何时能拿到 `device`。

**代价**：`readyForGPU()` 是 `abstract` 且返回 `Promise<any>`，导致大量子类写成空实现或 `throw not implemented`（`nodeObject.ts:124-132`、`camera/perspectiveCamera.ts:21-27`、`light/ambientLight.ts:14-24` ……）。

### 3.2 组织树：为什么 NodeSpace 独立于 NodeObject

```
RootGPU          持有 GPU 环境 + destroy 契约
  └ NodeSpace    只有「空间」：position / scale / rotate / quaternion / matrix / matrixWorld
      ├ NodeObject   加了「树」：parent / children / Entity / 动画 / stage
      └ BaseEntity   加了「渲染」：attributes / material / drawMode / storage
```

这个拆分的价值在于：**相机和光源继承 NodeSpace 分支（NodeObject），而"纯粹的空间量"可以被复用**。更关键的是 `NodeSpace` 同时被 `BaseEntity` 继承——意味着 **Entity 本身也有独立的矩阵**，可以被直接摆放到场景里而不必包一层 NodeObject。

**矩阵更新采用两级脏标记**（`nodeSpace.ts:387` + `nodeObject.ts:877`）：

- **本地脏**：`checkNeedUpdateLocalMatrix()` 比对 `position/scale/quaternion/rotate/rodrigues` 五个量与各自的 `_xxxOld` 副本（`nodeSpace.ts:379-383`），变了才重算 `matrix`。
- **世界脏**：`NodeObject.checkNeedUpdateWorldMatrix()` 比对 `_parentMatrixWorld` 与 `Parent.matrixWorld`（`nodeObject.ts:889`），只有父矩阵变了或本地脏了才重算 `matrixWorld`。

```844:861:src/we/core/organization/nodeObject.ts
    updateMatrixWorld() {
        // 父非 root：matrixWorld = Parent.matrixWorld × matrix（:848）
        // 父是 root：matrixWorld = matrix（:852）
    }
```

这是**链式传播的正确实现**：父没动，整个子树都不算。对静态场景性能极好。

**注意**：`update()` 是**深度优先递归**（`nodeObject.ts:775-777`），且子节点更新发生在父节点 `updateMatrixWorld` 之后，保证了正确性。缺点是没有"扁平化更新队列 + 并行"的优化空间。

### 3.3 罗德里格斯旋转（一个有意思的自定义设计）

`NodeSpace` 除了标准欧拉角/四元数，还提供了**绕任意轴旋转**：`RodriguesAnyPoint`（绕空间任意点）、`RodriguesZeroPoint`（绕原点）（`nodeSpace.ts:111-136`），在 `updateMatrix()` 最后统一应用（`nodeSpace.ts:317`）。

这是 three.js 没有的一层抽象，服务于"让物体绕某个 pivot 旋转而不用建父子节点"的场景。代价是矩阵合成逻辑变复杂，`updateMatrixWorldFroce()`（注意拼写）这种"强制更新"的旁路随之出现。

### 3.4 ECS：极简的 Manager 模式

```5:45:src/we/core/organization/manager.ts
export abstract class ECSManager<T extends I_UUID> {
    scene; device; list: T[];
    getByID(id); add(entity) { /* indexOf 去重后 push，并回填 entity._manager */ }
    remove(entity); checkDestroy(); abstract update(clock); count; getOneByUUID(uuid);
}
```

**这不是真正的 ECS**——没有 Component / Archetype 概念，`list` 里装的是完整对象，遍历时对多态对象逐个 `update()`。本质是"带自动回收的对象池 + 统一更新口"。

它的价值在于**统一了两点**：

1. **生命周期回收**：`checkDestroy()` 每帧剔除已 `_isDestroy` 的对象。
2. **更新顺序可控**：由 `Scene.update()` 显式编排（而不是靠对象自己注册）。

`FeatureManager`（`organization/featureManager.ts:22`）是它的一个特例——承载"不属于核心管线但也要每帧更新"的模块（**大气层**），由 `scene.otherManager` 持有并在 `update:828` 调用。这是一个很好的扩展点：**想加自定义全局系统，塞进 FeatureManager 即可，不用改 Scene**。

### 3.5 Command 体系：为什么要绕一层 DCG

WebGPU 的实际绘制需要 4 类东西：pipeline、bindGroup、vertex/index buffer、draw call。它们互相耦合（bindGroupLayout 必须匹配 pipeline layout，vertex layout 必须匹配 shader 的 `@location`）。

**DCG（`scene/command/DrawCommandGenerator.ts`，1663 行）的设计目标**是把这套耦合集中到一个地方，并且**全局去重**：

```297:330:src/we/core/command/DrawCommandGenerator.ts
    generateDrawCommand(values: IV_DC): BaseDrawCommand {
        // 1、initVertexPart   :580    → vertexBuffers + indexBuffer + location 字符串
        // 2、initUniformPart  :1145   → GPUBuffer + bindGroupLayout + bindGroup
        // 3、initShaderModule :1426   → include 展开 + MD5 → GPUShaderModule
        // 4、initPipeLine     :1565   → cacheFlag 命中则复用 RenderPipeline
        // 5、组装 IV_DrawCommand
    }
```

**两处关键的去重设计**：

- **着色器去重**：`MD5(code)` 作 key 存 `resources.shaderModuleOfString`（`:1449-1462`）。同一个材质变体的 1000 个实例共享一个 `GPUShaderModule`。
- **管线去重**：`cacheFlag = [md5VS, md5FS, topology, cullMode, stripIndexFormat, frontFace, depthStencilFlag, multisampleFlag]`（`:1640-1651`）。**[疑]** 其中 `depthStencilFlag` 拼成了字符串表达式，不同 depthStencil 描述可能算出同一字符串 → 错误命中缓存（详见 [04 P0-4](./04-问题缺陷与改进建议.md)）。

**System vs 非 System 两条路径**：带 `system` 的 DC 使用**固定 bindGroup 布局**（`group0=camera/light`、`group1=entity`、`group2=material`、`group3=IBL`，`:1157-1204`），这是引擎"约定优于配置"的核心——所有内置材质必须按这个约定放置 bindGroup，好处是 IB L/拾取/延迟渲染可以跨材质统一处理；代价是自定义材质必须遵守 `E_materialTypeForBindGroup` 的枚举约束。

### 3.6 ResourcesGPU：全局去重重地

`resources/resourcesGPU.ts` 维护约 **25 个 Map**，按 `E_resourceKind`（`:471-494`）分类：

| 类别 | Map | key |
| --- | --- | --- |
| 几何/索引 | `vertices` / `indices` / `verticesDynamic` / `indicesDynamic` | MD5 字符串 |
| uniform | `uniformBuffer` | `T_uniformEntries` 对象引用 |
| 纹理/采样器/材质（按名） | `textureOfString` / `samplerOfString` / `weTextureOfString` / `weMaterialOfString` | 名称字符串，如 `"default"`、`"linear"` |
| bindGroup / layout | `entriesToEntriesLayout` / `bindGroupToGroupLayout` / `entryLayoutOfGroup` | 对象引用 |
| 管线 / 着色器 | `pipeline` / `shaderModuleOfString` | cacheFlag / MD5 |
| 系统级 | `systemGroup0ByID` / `shadowmapOfID2BindGroup` | ID |

**Key insight：`model/**` 依赖 URL 或索引，`resourcesGPU` 依赖内容哈希或名称。** 前者是"用户视角的资源"，后者是"GPU 视角的资源"，两者通过 DCG 衔接。

**生命周期**：每个 `RootGPU` 子类都有一个 `mapList: {key, type, map?}[]`（`root.ts:63-67`），`destroy()` 遍历它回删：

```132:148:src/we/core/organization/root.ts
    destroy(): void {
        if (this._isDestroy) return;              // 幂等
        this._isDestroy = true;
        if (this.resourcesGPU) {
            for (let i of this.mapList) {
                if (i.map && this.resourcesGPU.getProperty(i.map)) {
                    (this.resourcesGPU[i.map] as Map<any, any>).delete(i.map);   // ← 有 bug
                } else {
                    this.resourcesGPU.delete(i.key, i.type);
                }
            }
        }
        this._destroy();
        if (this._manager) this._manager.remove(this);
    }
```

**[核] 这里有 bug**：第 138 行删的是 `i.map`（Map 的名字，如 `"textureOfString"`）而不是 `i.key`（真正的键）。**凡是带 `map` 字段的资源在 destroy 时都不会被真正释放**。这是显存泄漏的直接来源。

### 3.7 Scene：聚合根

`Scene`（`scene/scene.ts`，1391 行）**不继承任何类**，它是纯聚合根。初始化顺序是硬编码且**顺序敏感**的：

```452:543:src/we/core/scene/scene.ts
    navigator.gpu 检测 → requestAdapter → limits 校验 → features 过滤 → requestDevice
    → canvas 获取 + focus → getContext('webgpu') → getDPR → reSize()（内含 configure）
    → TextureManager → MaterialManager → FeatureManager → MemoryBlockManager
    → BPC / pointers
    → RenderManager          ← 注释明确要求要在 push DC 的 ECS 之前
    → resourcesGPU → AnimationManager → AnimationGroupManager
    → root = new RootManager + init
    → SkinsManager → EntityManager → LightsManager → CameraManager
    → InputManager → pickupManager → PostProcessManager → DCG → IBL
```

`initScene()`（`scene/fn.ts:5-37`）是唯一入口，做了三件事：`new Scene` → `await scene.init()` → **`runImmediately !== false` 时自动 `scene.run()`**。这就是为什么**绝大多数示例都不需要手动调用 `scene.run()`**。

### 3.8 内存管理：BOL / BPC / Pointer

这是 WE3D 最有野心的自研部分，目标是**把大量小 uniform 合并进少量大 GPUBuffer**，减少 bindGroup 切换与 buffer 数量。

```
BPC (BlockPointerCoordinator)          按 type 分桶管理多个 BOL
  └ BOL (BlockOffsetLength)            一个大的 Charon GPUBuffer + CPU 镜像 ArrayBuffer
      └ Pointer (I_pointerStruct)      一段逻辑上的连续区间 { pointerID, offset, byteLength }
```

- `BOL`（`bufferBlock/BOL.ts:75`）：内部有 `size{free,used,released,lastFree,total}`（`:212-224`）、`pointerIdList`、`pointerOffsetMap`；支持 `allocatePointer`（`:422`）、`releasePointer`（`:465`）、`rebuild`（`:261`）——**当碎片太多时会整块重建**。
- `BPC`（`BPC.ts:18`）按 `E_BOLBufferType` 分桶：`static / VS / dynamicVS / uniform / storage`（`base.ts:20-26`）；挑选策略是"取 `lastFree` 最大的块，不够就新建"（`:190-219`）。
- `Pointer`（`pointer.ts:14-49`）是给上层看的句柄，**带 CPU 侧视图** `cpuBufferView`，所以写 uniform 就是直接写 TypedArray，由 `BOL.update()`（`:394`）批量 `writeBuffer` 到 GPU。

**这个设计的好处**：材质写 uniform 是纯 CPU 内存写（零 GPU 调用）；**代价**：引入了"块重建"这个复杂状态机，任何 pointer 生命周期管理失误都会导致整块重建抖动。

分配流向：

| 用途 | 类型 | 位置 |
| --- | --- | --- |
| uniform（材质/实体） | `E_BOLBufferType.uniform` | `DrawCommandGenerator.ts:1355` |
| 顶点/索引 | `E_BOLBufferType.VS` | `DrawCommandGenerator.ts:739/843/939/991/1100` |
| 动态顶点 | `dynamicVS` | `DrawCommandGenerator.ts:622`（独立路径） |
| storage（骨骼矩阵等） | `createStorageBuffer` | `command/baseFunction.ts:135` |

### 3.9 着色器管理：SHR + 变体生成

`SHR/`（Shader Register）解决两个问题：**模块化 WGSL** 和 **着色器变体**。

- **静态收集**：`include.ts` 用 Vite 的 `?raw` 导入全部 `.wgsl`，聚合成 `WGSL_Include` / `WGSL_ShaderCode` / `WGSL_AliasShaderCode`（`:101` / `:172`）。
- **include 展开**：`formatShaderOfRenderMode()`（`shaderRegister.ts:139`）逐行处理 `#includeFile` / `#tag` / `#weStart` / `#weEnd` / `#renderMode`（`:146-204`）。**[疑]** `splitByLine` 硬编码 `\r\n`（`:336`）——LF 换行的文件会导致整个展开失效。
- **变体机制**：`#renderMode` 让你在同一份源码里按需裁剪 defer / MSAA / forward 的分支；材质通过 `getAliasShaderName(E_shaderRegisterAlianName.defer)` 拿到对应变体。
- **MD5 缓存**不在 SHR，在 DCG（见 §3.5）。

**设计评价**：用文本预处理实现着色器变体，简单直观、调试友好（可以把展开后的码打印出来）。代价是没有编译期检查，且字符串拼接的错误只能在运行时暴露（`shaderRegister.ts:365/387` 本该 throw 的地方降级成了 `console.log`）。

### 3.10 GBuffer 与多渲染方案

`E_GBufferNames`（`gbuffers/base.ts:20-37`）：`depth / color / id / normal / worldPosition / RMAO / albedo / emissiveIntensity / pbr`。

前向集合（`V_ForwardGBufferNames`，`:60-113`）：

| 通道 | 格式 | 用途 |
| --- | --- | --- |
| depth | `V_weDepthFormat` | 深度（reversedZ 时反向） |
| color | `V_weLinearFormat` | **线性色**（tonemapping 前） |
| id | `r32uint` | 拾取：打包 stageID/nodeID/instance |
| normal | `rgb10a2unorm` | 法线（紧凑） |
| pbr | `rgba32uint` | metallic/roughness/ao/emissive 打包 |

**三种 renderMode**（`scene.ts:275-283`）：

| 模式 | MSAA | 走哪些通道 |
| --- | :---: | --- |
| `forwardRender` | false | forward |
| `deferRender` | false | defer（先写 GBuffer，再 afterDefer 合成） |
| `MSAARender` | true | MSAA + MSAAinfo（只渲 color，`sampleCount:4`，depthLoadOp:'load' 不写深度） |

**注意**：README 说 MSAA 与延迟渲染暂不共存，代码里 MSAA 分支（`GBuffers.ts:250-281`）也确实只处理 color 附件——这是有意为之的简化。

### 3.11 光照与阴影

- **光源进 storage**：不是 per-light uniform，而是 `updateStructBuffer()`（`light/baseLight.ts:386-450`）按 **112 B stride** 写入一个动态数组，着色器侧是 `array<st_light>`（`shaders/system/system.wgsl:20,22`）。这是支持"1024 个光源"的技术前提。
- **实际上限**：`V_lightNumber = 8`（`base/coreDefine.ts:102`），而 `IV_Scene.lightNumber` 的注释说是 32（`scene/base.ts:22`），`IV_LightSManager.lightCount` 是未被读取的死字段（`lightsManager.ts:43`）。**三处说法不一致**，实际生效的是 8。
- **ShadowMap**：`texture_depth_2d_array`，1024×1024（`coreDefine.ts:98`），**点光源占 6 层**（立方体六面），其它占 1 层（`lightsManager.ts:255-297`）。每层配独立的 `light_shadowMapMatrix`（含 GPUBuffer + RPD，`:56-66`）。
- **PCSS**：`shaders/shadowmap/fn_pcss.wgsl:78` 实现，**纯 WGSL，没有 TS 侧参数类**；bias 硬编码 0.08（`fn_pcss.wgsl:290`），而 `IV_BaseMaterial.shadowMapBias`（`material/base.ts:115`）标了 todo 未接线。

### 3.12 动画系统

```
BaseAnimation（抽象，持 parent: NodeObject + interpolator + playState）
  ├ KeyFrameAnimation    采样结果写回 parent 的 Position/Rotate/Scale/Quaternion
  ├ MorphTargetAnimation  写 parent.MorphTarget 的 weights
  └ SkinAnimation         组合 Skeleton，写 parent._jointsMat
        └ Skeleton { joints: NodeObject[], inverseBindMatrices }
              update(): joint.matrixWorld × inverseBind → 共享 storage buffer
AnimationGroup：容器，广播 play/stop/pause/reset
```

**更新顺序是设计的关键**（见 §4）：`animationManager → animationGroupManager → root.update()（树变换）→ skinsManager → entityManager`。

原因很直白：**骨骼动画需要先有新的节点世界矩阵（由关键帧设置 + 树传播得到），才能算出关节矩阵，再写进 GPU 供顶点着色器使用**。顺序错一级，动画就会滞后一帧或完全错乱。

### 3.13 拾取：位打包的巧思

`pickup/pickup.ts` 的 ID 解包：

```168:172:src/we/core/pickup/pickup.ts
    stageID  = v >>> 30;                       // 高 2 bit
    nodeID   = (v & ((1 << 30) - 1)) >> 14;    // 中间 16 bit
    instance = v & 0x3fff;                     // 低 14 bit
```

一个 `r32uint` 里塞进了 stage / node / instance 三层信息，一次 `copyTextureToBuffer` 的 1×1 回读（`pickup.ts:188-219`）就能拿到完整拾取结果。这是典型的"用位运算换 IO 次数"的优化，很漂亮。

**[疑] 限制**：nodeID 只有 16 bit → 单 stage 最多 65536 个节点；instance 14 bit → 最多 16384 个实例。超大规模场景会溢出且**没有溢出检查**。

### 3.14 输入：三级优先级

`E_InputPriority`：`broadcastStart` / `intercept` / `broadcastEnd`（`input/base.ts:26-30`）。注册时按事件 × 优先级分层（`inputManager.ts:20-88`），分发时逐层遍历。

**[核] 实现有 bug**：`inputManager.ts:300/314/334/351/366/378` 的独占判定写成 `if (j == E_InputPriority.intercept)`，而 `j` 是**数组下标数字**，永远不等于字符串枚举值 → **intercept 优先级形同虚设**（详见 [04 P0-3](./04-问题缺陷与改进建议.md)）。

**三点观察**：

1. `Scene.update()` 的顺序是**手写硬编码**的（`scene.ts:790-839`），不是声明式依赖图。新增子系统必须人工插到正确位置，这是最容易出错的扩展点。
2. `update()` 与 `render()` 分离得很干净——**所有 CPU 侧计算集中在 update，render 只负责投递已经准备好的 command**。这个分离是正确的，也是未来做多线程/Worker 的前提。
3. `[疑]` `scene.ts:804` 的注释写"动画组更新需要在动画更新之前"，但代码排在之后（animationManager:803 → animationGroupManager:804）。注释与实现不符，需复核是哪一方有误。

## 五、数据流：从 `new Mesh()` 到 `draw()`

```
new SphereGeometry({radius:1})            → BaseGeometry.buffer{position,normal,uv,color,indeices}
new PBRMaterial({textures:{albedo:...}})  → BaseMaterial（尚未碰 GPU）
new Mesh({attributes:{geometry}, material, primitive, drawMode})
   ↓
await scene.add(mesh)
   ↓  NodeObject.addChild 分发（nodeObject.ts:546-596）
   ↓  BaseEntity → 包成 IV_Node{entity} → initNodeObject → entityManager.add
   ↓
await entity.init(scene, parent)
   ↓  setRootENV 拿 device / pointers / resourcesGPU
   ↓  readyForGPU()
   ↓    ├ 顶点 → BOL 分配 VS pointer → cpuBuffer 写入 → GPUBuffer
   ↓    ├ uniform → BOL 分配 uniform pointer（256 B 对齐）
   ↓    └ 材质 → WePbrMaterial() 异步加载纹理
   ↓
每帧 update()
   ↓  entity 计算是否被剔除 / 是否需要重排 DC
   ↓
scene.DCG.generateDrawCommand({...})
   ↓  ① initVertexPart   :580   vertices→layout+location串
   ↓  ② initUniformPart  :1145  pointer→GPUBuffer→bindGroup(group0~3)
   ↓  ③ initShaderModule :1426  #include展开 → MD5 → 缓存命中？
   ↓  ④ initPipeLine     :1565  cacheFlag → 缓存命中？
   ↓  ⑤ new DrawCommand
   ↓
renderManager 按 material 的 bindGroup 类型投到 forward / defer / transparent / MSAA 通道
   ↓
perDrawCommand.doDraw(optionOfDraw)   renderManager.ts:687/766
   ↓
queue.submit()
```

**这句话很重要**：WE3D **不是**"每帧重建 pipeline"，而是通过 **MD5 + cacheFlag 双重去重**把 pipeline/bindGroup/shaderModule 的数量压到"材质变体数"级别。理解了这一点，就能理解为什么 `resourcesGPU.clean()` 会导致下一帧全部重建（那是故意的——resize 或配置变更后必须失效重建）。

## 六、设计权衡与代价

| 决策 | 收益 | 代价 / 风险 |
| --- | --- | --- |
| 三段式初始化 + `RootGPU` 统一 destroy | 生命周期契约统一， theoretically 无泄漏 | `mapList` 回删实现有 bug → **实际泄漏**（§3.6） |
| 极简 ECS（list + 遍历） | 易理解、无 archetype 迁移开销 | 没有数据局部性，万级对象时缓存不友好；更新靠深度递归 |
| 固定 bindGroup 约定（group0~3） | IBL / 拾取 / 延迟渲染可跨材质统一处理 | 自定义材质自由度受限；违反约定只能运行时炸 |
| BOL 内存池合并 uniform | buffer 数量少、写 uniform 零 GPU 调用 | 引入"块重建"状态机，调试困难；pointer 泄漏会拖垮整块 |
| 文本预处理做着色器变体 | 直观、可打印展开结果 | 无编译期检查；硬编码 `\r\n` 有平台风险 |
| 手写 `Scene.update()` 顺序 | 顺序完全可控 | 扩展成本高；注释与实现已出现不一致（`:804`） |
| 位打包拾取 ID | 1 次回读拿 3 层信息 | 位宽上限无检查，超规模溢出静默 |
| 单一 Charon Scene 聚合根 | 一切可达（`scene.xxxManager`） | **`Scene` 1391 行职责发散**；无法多 Scene 共存 |
| 严格 pin WebGPU | 不留历史包袱 | 无降级路径，旧浏览器直接白屏（无 `navigator.gpu` 提示） |

## 七、与主流引擎的定位差

| 维度 | three.js | Babylon.js | **WE3D** |
| --- | --- | :---: | :---: | :---: |
| 生态/loader | 极丰富 | 丰富 | 仅 glTF（且待迁移） |
| WebGPU 原生度 | WebGL 为主 | 双栈适配 | **纯 WebGPU** |
| 内存管理 | 无显式池 | 部分 | **BOL 显式池** |
| 内置高级渲染 | 靠插件 | 部分内置 | **大气/体渲染/IBL 内置** |
| 编辑器 | 社区版 | Inspector | 无（todo） |
| 抽象层级 | 薄（贴近 GL） | 厚 | **中偏厚，且暴露下层**（可以直接拿 `scene.DCG`、`pointers`） |

**WE3D 的一个独特体验**：它既提供了 `scene.add(mesh)` 这种高层 API，又**允许直接访问 `scene.pointers.createPointer(...)`、`scene.DCG.generateDrawCommand(...)`**。这种"上下都开门"的设计对个人开发者很友好（学习曲线可按需切换），但也意味着 API 边界模糊，文档压力更大。

## 八、给内核改动者的五条建议

1. **先确定你的子系统挂在 `update()` 的哪一步**（`scene.ts:790-839`）。位置错了，症状往往是"慢一帧"或"偶尔错乱"，极难定位。
2. **任何 GPU 资源创建都要更新 `mapList`**，否则 destroy 时不会释放。鉴于现有实现有 bug，建议先修再利用。
3. **材质必须遵守 group0~3 约定**，否则无法享用 IBL / 拾取 / 延迟渲染的公共路径。
4. **不要动 `update`/`render` 的顺序 unless 有截图基线**。顺序调整的影响面是全引擎的。
5. **改完内核要重新生成 API 文档**——见下一节，命令是 `cd doc && npm run make`。

→ 详细的缺陷清单与修复建议见 [04-问题缺陷与改进建议.md](./04-问题缺陷与改进建议.md)

## 九、文档生成：进入 `/doc` 目录执行 `npm run make`

### 9.1 唯一正确的命令

```bash
cd doc
npm run make
```

> ⚠️ **注意：生成文档不是 `npm run build`。**
> 根项目的 `npm run build`（`tsc && vite build`）是**构建引擎产物**，与文档无关；
> 文档生成是 `doc` 这个**独立工具项目**里的 `npm run make`。两者不要混淆。

`doc/package.json` 中的定义：

```6:8:doc/package.json
  "scripts": {
    "make": "npx typedoc  --tsconfig ../tsconfigdoc.json   "
  },
```

即：**必须 `cd` 到 `doc` 目录后再执行**，因为它依赖相对路径 `../tsconfigdoc.json`（指向仓库根同级配置）。在仓库根直接跑 `npm run make` 会失败（根 `package.json` 没有 `make` 脚本）。

### 9.2 链路

```
cd doc && npm run make
   │
   └─ npx typedoc --tsconfig ../tsconfigdoc.json
         │
         ├─ 读取 doc/tsconfigdoc.json 的 typedocOptions
         │    entryPoints: ["../src/we/**/*.ts"]      ← 扫描完整核心引擎
         │    out:          "../docs"                  ← 输出到仓库根的 /docs
         │    skipErrorChecking: true                  ← 即使有 TS 错误也继续生成
         │
         └─ 生成 → /docs（714 个 API 页面 + index/modules/hierarchy）
```

| 环节 | 值 |
| --- | :---: |
| 工具项目 | `/doc`（`WE3D-doc` v0.0.1，自有 `package.json` / `package-lock.json`，依赖 typedoc ^0.26.3） |
| 生效配置 | **`doc/tsconfigdoc.json`**（唯一真相源，:30-36） |
| 扫描范围 | `../src/we/**/*.ts` —— 覆盖本文档涉及的全部核心模块 |
| 输出目录 | `../docs` |
| 线上地址 | https://webgpuengine.github.io/WE3D/ |
| 发布版仓库 | https://github.com/WebgpuEngine/WE3DDoc（`doc/用法.txt:8-14`） |

### 9.3 与本目录文档的分工

| 想查什么 | 去哪 |
| --- | :---: |
| 某个类/接口的字段叫什么、什么类型 | **`/docs`**（typedoc，逐符号，自动生成） |
| 该怎么用、该插在 `update()` 的哪一步、有哪些坑 | **本目录**：`01` 设计 · `02` 用法 · `03` 字段速查 · `04` 缺陷 |
| 字节布局、常量数值、字段默认值 | `core/README`「关键数字」+ `03-API速查手册` |

`docs/` 是**逐符号的 API 参考**，回答不了"为什么这么设计"和"该插在哪里"——这正是本目录存在的原因。两者互补，不要互相替代。

```bash

# 2、同步注释（typedoc 抽取的是 JSDoc）
# 3、重新生成文档

# 4、确认产物更新
```

**两处已知坑**（详见 [04 P1-13](./04-问题缺陷与改进建议.md)）：

- `doc/typedoc.json` 的入口是 `../src/core/**`、`../src/model/**`，**路径已过期**（实际是 `src/we/*`）。`npm run make` 走的是 `tsconfigdoc.json` 所以不受影响，但**不要照 `typedoc.json` 手动跑 `npx typedoc`**。
- `skipErrorChecking: true` 意味着**即使源码有 TS 错误，文档也会照常生成**——文档"能生成"不代表"代码能编译"。当前 `npx tsc --noEmit` 有 1991 个错误，但 `/docs` 照样是完整的（见 [04 P0-0](./04-问题缺陷与改进建议.md)）。
