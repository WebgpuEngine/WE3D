### 2.3 lint / format（原 P0-5，已搭，format 延后）

- `eslint`（`@eslint/js` + `typescript-eslint` + `eslint-config-prettier`）+ `prettier` 已配置，门禁仅覆盖 `src/we`（不含 `examples/`、`docs/`、`src/@loaders.gl/`）。
- `npm run format` / `format:check` 脚本已补齐，但按约定**延后至 e2e 回归完成后单独执行**（`pending-work.md` #1）——属收尾边角项，非阻塞。

### 2.4 e2e 回归（新能力，但覆盖有缺口）

- Playwright 双配置：`playwright.config.ts`（GPU 硬件 headless 版，8 workers，真实 GPU）+ `playwright.software.config.ts`（SwiftShader 软件版，2 workers），共用 `tests/e2e/baseline/`。
- 基线由 **GPU 硬件版** `npm run test:baseline` 产出并**提交 git**；软件版与 GPU 基线做差值检测。
- `e2e-cases/` 按子目录组织：`animations / baseEntity / camera / deferRender / forward / geometry / IBL / instance / lights / material / MSAA / postprocess / primitive / shadow / texture / transparent` + 自动生成 `index.html`。
- **关键缺口**：`e2e-cases/` 内**无 `model/gltf` 目录**，对 `createGLTFModel` / `GltfDataAtLoaders` 的引用为 **0**。35 个 gltf 示例仍躺在 `examples/model/gltf/`，**未被纳入自动化回归**。

### 2.5 CI / 发布（原 P0-4，已搭）

- `.github/workflows/ci.yml`：`push/PR` → `ci:no-e2e`（lint+typecheck+test+check:exports+build:lib，无 e2e/文档）。
- `.github/workflows/release.yml`：`v*` tag → `build:lib` + `docs:build:force` + 回写 `docs/`。
- 本地 `npm run ci`（含 e2e）/`ci:no-e2e` 与云端等价；`publish:if-new` + `prepublishOnly` 提供手工发布兜底。

### 2.6 文档与版本（原 P1-10 / §3.5，已理顺）

- 版本 `0.0.0`→`0.0.2`，去除 `private:true`，补齐 `exports`/`types`/`files`，与 README 发布声明不再矛盾。

| 决策记录 | `pending-work.md` #4：`@loaders.gl` 整体迁移**决策延后（⏸ 已暂停/后期）**，迁移前保持现状勿动 |

### 3.2 04 号方案仍然有效，但前置条件未满足

04 号方案（用 `@gltf-transform/*` 取代 `@loaders.gl/*`）的**技术论证依然成立**：`ModelDataLoader` 抽象使 `gltf.ts` 几乎不用改，改造面仍是"1 新文件 + 1 处工厂 + 删 fork"。

**但 04 方案的关键前置——"Phase 0 先建 gltf 回归基线"——至今未做**，且现状比 2026-09-23 更棘手：

- 旧分析时，35 个 gltf 示例统一在 `examples/model/gltf/`，补基线只需对它们截图。
- 现在示例承载方式已分化：`examples/` 是 vite dev 站点，`e2e-cases/` 是 Playwright 回归对象，而 **gltf 示例两个都没进**——既没迁移进 `e2e-cases/`，也没被 e2e 索引。
- 这意味着：一旦启动迁移，**没有可对照的自动化基线**，04 的验收标准 #1（35 示例逐像素一致）和 #2（accessor 数值快照一致）**将无基准可 diff**。

**结论**：04 方案可直接复用，但**执行顺序必须前移"补 gltf e2e 基线"**——先把这些示例迁入 `e2e-cases/model/gltf/` 并生成 GPU 基线，再开 Phase 1。原 04 的 Phase 0 现在落地难度更高，不能跳过。

### 3.3 glTF 模块的既有缺陷（03 号文档 D1–D8）仍未修

由于迁移未启动且迁移后才有基线可对照（04 方案明确的"先迁移、后修缺陷"原则），03 号文档列出的 **D1–D8 全部仍处于未修复状态**，其中 3 个会直接产生可见渲染错误：

- **D1** 单 mesh 多 primitive 被覆盖（高）
- **D2** LINE_LOOP 索引转换缺失 / 死分支（中）
- **D7** `||` 默认值吞掉合法的 `0`（金属度 0 → 全金属，中）
- D3 / D4 / D5 / D6 / D8（中/低）

这些可在迁移后"有基线"时集中修，但**现在仍是真实的渲染正确性 bug**。

## 八、一句话总结（修正版）

WE3D 已跨过工程可信化门槛——`tsc` 归零、lint/单测/e2e 双配置/CI/发布/文档全链路齐备，**工程下限不再是产品化阻塞**；但两项核心遗留未动：① glTF 解析层仍是本地 fork 改 `dist`（04 方案有效、延后执行）；② 最脆弱的模型加载路径**至今没有自动化回归**（35 个 gltf 示例未进 `e2e-cases`）。下一步投入产出比最高的动作是**先补 gltf e2e 基线，再启动 glTF-Transform 迁移**——而不是再堆渲染特性。
