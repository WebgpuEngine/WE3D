## 一、项目是什么

WE3D 是一个**用 TypeScript 直接封装 WebGPU API 的 Web 端 3D 渲染引擎**，不依赖 three.js / Babylon.js，也没有 WebGL 后向兼容包袱。按 README 的自述，它由"基础引擎"和"编辑器"（todo）两部分组成，基础引擎又分五个模块：核心功能、图形学功能、模型功能、物理引擎整合、动画管理。

工程形态是一个 **Vite + TypeScript 的单体仓库**，同时充当：源码仓库 + 示例站点（`examples/`，219 个文件）+ 静态资源仓库（`public/`）+ npm 发布源（README 声称已发布 `we3d` / `webgpu-we3d`）。

关键事实核对：

| 构建 | `tsc && vite build`（vite 7.1）。**[核] `npx tsc --noEmit` 当前 1991 个错误（`src/we` 231 + `examples` 1760）→ `npm run build` 必然失败**，详见 §3.5 |
| 测试 | **没有任何测试文件**；`ts-jest` 已安装但未配置、未使用 |

## 二、架构全景

### 2.1 三条主线

引擎的组织可以归纳为三条互相咬合的主线：

```
【组织树 Organization】         【命令集合 Command】            【ECS 管理器 Managers】
RootGPU (抽象根/资源持有者)      DrawCommandGenerator (DCG)     Scene 内部持有十余个 Manager
  └ NodeSpace (TRS/四元数/矩阵)   ├ DrawCommand                 ├ textureManager
      └ NodeObject (场景节点)     ├ ComputeCommand              ├ materialManager
          ├ RootManager(scene.root)├ CopyCommand                ├ animationManager
          ├ BaseModel (gltf 等)   └ 由 entity+material+geometry ├ animationGroupManager
          └ BaseLight             组装 pipeline / bindGroup    ├ skinsManager
      └ BaseEntity (可渲染)                                     ├ entityManager
          └ Mesh / Lines / Points                               ├ lightsManager
                                                                ├ cameraManager
                                                                ├ postProcessManager
                                                                └ memoryBlockManager(BOL/BPC)
```

### 2.2 渲染主循环

位于 `src/we/core/scene/scene.ts`：

```
run() → requestAnimationFrame(perFrameRun)
  clock.update()
  onBeforeUpdate()      // resize、renderManager.clean
  pickup()              // GPU 拾取
  update()              // 顺序强耦合：
      texture → material → animation → animationGroup → root.update()（树变换）
      → skins → entity → BPC → memoryBlock → lights → camera → other(大气)
      → postProcess → 包围盒/BVH
  onAfterUpdate()
  onBeforeRender()
  render()              // 仅调用 renderManager.render()
  onAfterRender()
  showGBuffersVisualize() → renderToSurface() → cleanUp()
```

`update()` 的顺序是**手写硬编码**的（依赖顺序靠注释与经验维护），这是性能可控但脆弱的设计——新增子系统必须人工插到正确位置，容易出错。

### 3.2 做得好的地方

1. **WebGPU 原生，无历史包袱。** 直接使用 `GPUDevice / GPUBuffer / GPUTexture / GPURenderPipeline`，没有为了兼容 WebGL 而做的抽象妥协。反向 Z、MSAA、storage buffer 骨骼矩阵等都用到了 WebGPU 的特性。
2. **Command 抽象统一了渲染入口。** Draw / Compute / Copy 三类命令 + DCG 统一生成 pipeline 与 bindGroup，后处理、阴影、延迟渲染走同一套机制，扩展新通道的成本低。
3. **`ModelDataLoader` 抽象是真正的架构亮点。** 模型解析（`GltfDataAtLoaders`）与引擎对象构建（`GLTFModel`）完全解耦，OBJ / FBX 只需实现同一抽象类即可接入。这一点直接决定了本次 glTF-Transform 迁移的低成本。
4. **GPU 资源生命周期有统一出口。** `ResourcesGPU` 按 `E_resourceKind` 分类缓存，`RootGPU.destroy()` 通过 `mapList` 回删，思路正确。
5. **特性探索很有野心。** 大气层同时实现了 Bruneton / Hillaire LUT / 实时积分三套方案并叠加体积云、丁达尔、云阴影；体渲染同时实现了 3D 纹理与 ray march。这类内容在同类引擎里少见。

### 3.3 最大的技术债：本地 fork 并直接改 `dist`

**现象**

- `package.json` 中：`"@loaders.gl/draco": "./src/@loaders.gl/draco"`、`"@loaders.gl/gltf": "./src/@loaders.gl/gltf"`，即两个包是**仓库内的本地目录**。
- 这两个目录下**没有 `src/`，只有 `dist/`**（`dist/lib/**`、`dist/libs/**`、`dist/workers/**` 与打包产物 `dist.min.js` / `dist.dev.js` / `index.cjs`）。
- 也就是说，所有定制都是**直接改编译产物里的 JS**，没有源码、没有 patch 记录、无法重新构建、无法 rebase 上游。
- `src/@loaders.gl/readme.txt` 自述："4.3.4 版本的 draco 和 gltf 不能正确返回解压 draco 的内容；修改了 @loader.gl 的内容，修正了问题，但不反馈，因为其他部分的 draco 与 gltf 机制冲突。"
- 另有运行时资源 `public/@loaders.gl/`（Draco worker）。

**改了什么**（在 dist 中定位到的三处关键补丁）

1. `src/@loaders.gl/draco/dist/lib/draco-parser.js`：把 `DRACO_TO_GLTF_ATTRIBUTE_NAME_MAP` 中除 `POSITION` 外的映射（`NORMAL` / `COLOR_0` / `TEXCOORD_0`）全部注释掉。
2. `src/@loaders.gl/gltf/dist/lib/extensions/KHR_draco_mesh_compression.js`：`decompressPrimitive` 不再把解码出的 accessor **对象**塞进 `primitive.attributes`，而是写回 `scenegraph.gltf.json.accessors[原索引]`，保持索引号不变。
3. `src/@loaders.gl/gltf/dist/lib/api/post-process-gltf.js`：`_resolveAccessor` 给非 Draco 路径的 accessor 注入 `value` 字段（从 bufferView slice 出一份 TypedArray）。

**引擎侧的对应 hack**（`src/we/model/gltf/gltfAtLoaders.ts`）

```279:296:src/we/model/gltf/gltfAtLoaders.ts
    getAccessorForByte(index: number): Uint32Array | Int32Array | Float32Array {
        let accessor = this.gltf.getAccessor(index);
        let arrayBuffer;
        //此处使用了修改版本的@loader.gl/gltf，增加了accessor.value的类型
        // @ts-ignore
        if (accessor.value == undefined) {
            try {
                arrayBuffer = this.gltf.getTypedArrayForAccessor(index);
            }
            catch (error) {
                console.error(`gltf accessor index:${index} 's bufferView not support`);
                throw error;
            }
        }
        else {
            // @ts-ignore
            arrayBuffer = accessor.value;
        }
```

即：引擎**依赖第三方库的一个私有、非约定字段 `accessor.value`** 来区分"Draco 解码后的 accessor"与"普通 accessor"，并用 `@ts-ignore` 绕过类型检查。同样逻辑在 `getAccessorForArray()` 中又重复了一遍。

**为什么这是 P0 级问题**

- 无法升级：上游一升级就被覆盖，补丁丢失。
- 无法审查：改动在压缩/编译后的 JS 里，diff 不可读。
- 不可重建：无 `src`，CI 无法复现，换机器即可能失效。
- 传染性：`accessor.value` 的私有约定泄漏到了业务代码，任何"为什么这里能跑"的疑问都要回溯到 dist 里找答案。
- 认知负担：新贡献者看到 `package.json` 指向 `./src/@loaders.gl/*` 时无法判断这是 fork 还是源码。

**这正是本次 glTF-Transform 迁移要解决的核心问题。**

### 3.5 文档生成链路与构建现状

**`/doc` 是工具项目，不是杂物目录**（`doc/package.json`：`"name": "WE3D-doc"`, `"make": "npx typedoc --tsconfig ../tsconfigdoc.json"`）：

**生成命令**：**`cd doc && npm run make`**——注意是进入 `doc` 目录后执行 `make`，**不是根项目的 `npm run build`**（后者是 `tsc && vite build`，构建引擎产物，与文档无关）。

**`/docs` 是已生成的产物**，覆盖完整核心引擎：classes 151 / interfaces 176 / modules 194 / functions 89 / types 41 / variables 34 / enums 29，共 **714 个 API 页面** + `index.html` / `modules.html` / `hierarchy.html`。

**两个真实问题：**

1. **[核] `npm run build` 当前必然失败。** `npx tsc --noEmit` 实测 **1991 个错误**（`src/we` 231、`examples` 1760）。根 `tsconfig.json` 的 `include` 是 `["src", "examples"]` 且开了 `noUnusedLocals/noUnusedParameters`，`build` 脚本是 `tsc && vite build`，tsc 非零退出后 `&&` 直接中断。
   - **好消息**：`src/we` 的 231 个里，**只有 1 个是真实类型错误**——`src/we/core/gbuffers/GBuffers.ts:9` 从 `./base` 导入了不存在的 `V_TransparentGBufferNames`；其余 230 个全是 `TS6133/TS6192`（未使用的导入与变量）。
   - `examples` 的 1760 个里既有 unused 也有真实错误（如 `E_AnimationPlayType` 不含 `"count"`、`NodeObject` 未从 `organization/root` 导出）。
   - **修复成本远低于数字看起来那么高**：先修 1 个真实错误，再把 230 个 unused 批量清理（多数是删 import），`examples` 侧可先加 `exclude` 或单独放宽 `noUnusedLocals`。
2. **`.todo` / `.backup` 后缀是一种"手工排除编译"手段。** `log.txt` 里编译不过的 `TTP.ts`、`mulitibl.ts`、`shaderMaterial.ts`、`capsuleGeometry.ts`，现在分别叫 `TTP.ts.backup`、`mulitibl.ts.todo`、`shaderMaterial.ts.todo`、`capsuleGeometry.ts.todo`——**改名正是为了让它们不被 `tsc` 的 `include: ["src"]` 命中**。理解这一点很重要：清理这些文件时不能简单删掉，要先确认其中逻辑是否已迁移（例如 `TTP.ts` 的透明渲染逻辑、`mulitibl.ts` 的多 IBL 逻辑），否则会丢失尚未完成的设计。

## 四、改进优先级建议

### P0（阻塞产品化，1～2 周）

1. **让 `npm run build` 能跑通**（约 1～2 d，性价比最高）。当前 `tsc` 1991 错误，`src/we` 侧只有 1 个真实类型错误（`gbuffers/GBuffers.ts:9` 的 `V_TransparentGBufferNames`），其余 230 个是 `TS6133/TS6192` 未使用变量 —— 批量删 import 即可；`examples` 侧 1760 个建议先用 `tsconfig` 的 `exclude` 或单独放宽 `noUnusedLocals` 隔离，再逐步清理。见 §3.5。
2. **消灭本地 fork**：迁移到 `@gltf-transform/*`（见 [04 号文档](./04-迁移到glTF-Transform方案.md)），删除 `src/@loaders.gl/**` 与 `public/@loaders.gl/**`。
3. **建立最小可信回归**：引入 vitest（已装 `ts-jest` 可替换）+ 至少覆盖模型解析层；对 35 个 gltf 示例做截图基线（可用 Playwright 已有能力）。
4. **CI + lint**：GitHub Actions（tsc + lint + test），`eslint` + `prettier` 一次性格式化（单独一个 commit，避免污染后续 diff）。**CI 里的 tsc 门禁先设"错误数不增加"**，避免一上来就红。
5. **清理 `console.log` 与死代码**：先 `console.log` → 分级 logger；再删注释块。

### P1（工程化基本面，2～4 周）

6. 拆分巨型文件：`DrawCommandGenerator` 按职责拆（pipeline 生成 / bindGroup 生成 / vertex layout / command 组装）；`Scene.update()` 的硬编码顺序改为可声明的依赖图。
7. 类型治理：给 `ModelDataLoader` 定义 glTF 2.0 的 TypeScript 类型（可先用 `glTF-Transform` 的类型或 `@types/gltf`），逐步消灭 `any`；开启 `strict` 相关选项。
8. 统一资源生命周期：定义 `dispose()` 契约 + 一个 debug 模式下的资源计数面板，杜绝 GPU 资源泄漏。
9. 版本号与发布：修正 `package.json` 版本、`private` 与 README 声明的矛盾，落地 npm 发布流水线。
10. **修 `doc/typedoc.json` 入口路径**（`../src/core` → `../src/we`），或干脆删除该文件只保留 `tsconfigdoc.json` 一个真相源；删除 `typedoc copy.json` 与 `old.tsconfig.json`。并在 `doc/用法.txt` 与 README 中明确写出命令是 **`cd doc && npm run make`**（不是 `npm run build`）。

### P2（产品化，1～2 月）

11. 文档体系：把 `cd doc && npm run make`（typedoc）接入 CI 自动重建 `docs/` 并发布；补架构文档（[core/01 §9](./core/01-设计思路.md) 记录了生成链路）、用法教程、贡献指南。注意区分：`docs/` 是逐符号 API 参考，架构/用法类文档需另建。
12. 示例站：把 `examples/` 做成可检索的在线示例站（仓库已有 `scripts/generate-examples-json.mjs`，可复用）。
13. 编辑器（README 中的 todo）：材质 / 动画 / 场景编辑器 + 构建管理器。这是从"引擎"走向"产品"的关键一步，建议先做场景编辑器（复用已有的组织树与拾取能力）。

> **清理 `.todo` / `.backup` 文件前必读**：这些后缀是**手工排除 `tsc` 编译**的手段（见 §3.5）。`TTP.ts.backup`、`mulitibl.ts.todo`、`shaderMaterial.ts.todo`、`capsuleGeometry.ts.todo` 里含有未完成的设计（透明渲染 TT 双缓冲、多 IBL、volume shader 变体、胶囊体），删除前需确认逻辑是否已迁移。

### 模型层的独立建议（不影响主线的顺手修复）

- 单 mesh 多 primitive 覆盖（`gltf.ts:1175`，后一个 primitive 覆盖前一个）。
- LINE_LOOP 索引转换缺失（`gltf.ts:1413-1437` 把 `mode === 2` 映射为 `indexTriangleList`，导致 `indexLineLoop` 分支成为死代码）。
- accessor bundle 缓存 key 不一致（`gltfAtLoaders.ts:245` 用 `accessorID` 判断、`:250/255` 用 `aliaseID` 写入，缓存永不命中）。
- 皮肤动画与动画组全量绑定（`gltf.ts:249-258`）。
- 索引统一转 `uint32`，`uint16` 未保留，浪费带宽。

## 五、一句话总结

WE3D 的**技术上限已经相当高**——它证明了一个小团队可以在 WebGPU 上从零做出覆盖 PBR、延迟渲染、大气散射、体渲染的完整引擎，而且**API 文档其实已经建好**（`/docs` 714 页 typedoc 站）；但它的**工程下限还很低**——`npm run build` 当前跑不通（`tsc` 1991 错误）、没有测试、没有 CI、第三方库被 fork 后直接改 dist。当前阶段投入产出比最高的动作，不是再增加渲染特性，而是把工程化补齐：**先让 build 变绿（1～2 d）→ 再消灭本地 fork → 最后建立回归基线**。
