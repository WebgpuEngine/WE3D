## 一、产品定位

### 1.1 一句话定义

**WE3D 是一个用 TypeScript 编写的 WebGPU 原生 3D 渲染引擎，为需要在浏览器端呈现高质量三维内容的开发者提供渲染、动画、物理与资产管理能力。**

### 1.2 产品边界

```
┌──────────────────── WE3D ────────────────────────────┐
│  编辑器（todo，规划中）                                │
│   材质编辑器 / 动画编辑器 / 场景编辑器 / 构建管理器     │
├──────────────────────────────────────────────────────┤
│  基础引擎（当前主体）                                  │
│   ① 核心功能   场景/实体/纹理/材质/相机/光源/阴影/后处理 │
│                ECS / GPU 拾取 / AA / 色彩空间 / BVH    │
│   ② 图形学     IBL / SH / 大气散射 / 体渲染 / 体积云    │
│   ③ 模型       glTF(glb) / OBJ(todo) / FBX(todo)      │
│   ④ 物理       rapier 整合（进行中）                    │
│   ⑤ 动画       关键帧 / 骨骼 / 变形目标 / 粒子(todo)    │
└──────────────────────────────────────────────────────┘
           底层：WebGPU + WGSL（无 WebGL 兼容层）
```

### 1.3 差异化主张

| 主张 | 依据 |
| --- | --- |
| **WebGPU 原生，不为 WebGL 妥协** | 全仓库直接调用 `GPUDevice / GPUBuffer / GPUTexture`，92 个 WGSL 着色器；反向 Z、storage buffer 骨骼矩阵、MSAA + 延迟渲染等均按 WebGPU 语义实现 |
| **自研架构，非 three/Babylon 套壳** | README 自述"参考了 Babylon、three、cesium、UE"但为独立设计与实现 |
| **渲染特性覆盖广** | 大气散射三套方案、体渲染双方案、IBL + SH、PCSS 阴影、GPU 拾取、BVH，在同规模项目中少见 |
| **模型资产链路可扩展** | `ModelDataLoader` 抽象层让 glTF/OBJ/FBX 共用一套引擎构建流程（见 [03 号文档](./03-gltf模块深度分析.md)） |

## 二、目标用户与场景

### 2.1 用户画像

| 画像 | 特征 | 核心诉求 | WE3D 匹配度 |
| --- | --- | --- | --- |
| **A. Web 3D 探索者** | 个人开发者、学生、技术博主 | 想用最新 WebGPU API 做东西，愿意读源码 | ★★★★★（源码可读、示例丰富） |
| **B. 数字孪生 / 可视化开发者** | 工业、园区、设备可视化 | 加载 glTF 模型 + 动画 + 拾取交互 + 大场景 | ★★★☆☆（模型与拾取已有，LOD/流式加载/地理坐标待补） |
| **C. 科研与仿真可视化** | 气象、流体、医学体数据 | 体渲染、等值线、流线、云图 | ★★★★☆（体渲染双方案、大气、仿真示例已存在，是明显长板） |
| **D. 游戏 / 互动内容开发者** | 独立游戏、营销互动页 | 完整工具链、编辑器、性能、跨浏览器 | ★★☆☆☆（编辑器未做，浏览器覆盖受限） |
| **E. GIS / 地理空间** | 地图、实景三维 | 地理坐标、瓦片、地形 | ★☆☆☆☆（README 列为 todo） |

**建议**：当前阶段主攻 **A + C**，兼顾 **B**。C 类（科研/仿真可视化）是 WE3D 最被低估的定位——大气散射、体渲染、体积云这些能力在 three.js 生态里都要额外找插件，而 WE3D 内置。

### 2.2 典型用例（已由 `examples/` 验证的能力）

1. **加载并播放 glTF 动画模型**：`createGLTFModel()` → `scene.add()` → `AnimationGroup[i].play("loop")`（Fox、Hen、LittlestTokyo、骨骼、变形目标均已跑通）。
2. **物理真实的大气与天空**：Bruneton / Hillaire LUT / 实时积分三选一，叠加体积云、丁达尔光效、云阴影。
3. **体数据可视化**：3D 纹理采样与 ray march 两种方案（仿真云图、等值线、流线示例）。
4. **PBR 材质 + IBL + SH**：预滤波 cubemap + 球谐光照 + 天空盒。
5. **GPU 拾取交互**：ID buffer 渲染 + 回读，配合 BVH 与物理引擎做 CPU ray。
6. **物理驱动动画**：rapier 整合（进行中，已有 demo 截图）。

## 四、竞品对比

| 引擎 | 技术栈 | 成熟度 | 生态 | WE3D 的相对位置 |
| --- | --- | --- | --- | --- |
| **three.js** | WebGL 主 + WebGPU 后端 | 极高 | 极大（loader/后处理/编辑器生态完整） | WE3D 在大气/体渲染等"内置高级特性"上有优势；生态、文档、稳定性差距巨大 |
| **Babylon.js** | WebGL + WebGPU | 很高 | 大（含 Playground、Inspector、编辑器） | Babylon 的 WebGPU 支持与工具链都领先；WE3D 胜在纯粹与可读 |
| **Orillusion** | WebGPU 原生 | 中 | 中（国内社区） | 定位最接近的直接对手；同为 WebGPU 原生 + TS |
| **CesiumJS** | WebGL（WebGPU 探索中） | 极高 | 大（GIS 领域事实标准） | WE3D 无地理能力，暂不竞争 |
| **PlayCanvas** | WebGL + WebGPU | 高 | 大（含云编辑器） | 编辑器是 PlayCanvas 核心壁垒，WE3D 编辑器尚未起步 |

**结论**：WE3D 不宜在"通用 Web 3D 引擎"赛道与 three.js / Babylon 正面竞争。建议走**差异化垂直路线**：

> **"WebGPU 原生的科学可视化 / 仿真渲染引擎"** —— 以大气、体渲染、体积云、大规模仿真数据为卖点，同时保持通用 3D 能力。

## 八、附录：最小上手示例（现状 API）

```ts
import { initScene } from "./src/we/core/scene/fn";
import { PerspectiveCamera } from "./src/we/core/camera/perspectiveCamera";
import { DirectionalLight } from "./src/we/core/light/DirectionalLight";
import { AmbientLight } from "./src/we/core/light/ambientLight";
import { createGLTFModel } from "./src/we/model/gltf/gltf";

// 1. 场景
let scene = await initScene({ initConfig: { canvas: "render", reversedZ: true } });

// 2. 光与相机
await scene.add(new AmbientLight({ color: [1, 1, 1], intensity: 0.7 }));
await scene.add(new DirectionalLight({ color: [1, 1, 1], direction: [0, 0, 5], intensity: 0.5 }));
await scene.add(new PerspectiveCamera({
  fov: (2 * Math.PI) / 5, aspect: scene.aspect, near: 0.01, far: 100,
  position: [0, 0, 5], lookAt: [0, 0, 0], controlType: "orbit",
}));

// 3. 模型
let gltf = await createGLTFModel({
  scene,
  url: "/models/gltf/model/Fox/glTF-Binary/Fox.glb",
  debug: true,
});

// 4. 实例化 + 播放动画
let instance = await scene.add(gltf, { position: [0, 0, 0], scale: [0.1, 0.1, 0.1] });
instance.AnimationGroup[2].play("loop");
```

可选项：

- `dataTypeOfAttribute?: "BOL" | "inModel"` —— 顶点数据是交给引擎内存块管理（BOL）还是由模型内部持有 GPUBuffer（默认 `inModel`）。
- `createGLTFModel(input, { beforeGltfInit, afterGltfInit })` —— 在解析后/构建后插入自定义逻辑（示例中用于改写材质）。
