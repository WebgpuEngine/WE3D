> **评估性质**：独立复核。结论只基于当前仓库源码、配置、实测门禁输出、git 历史与 README/设计约定文档；**未参考 `design/workBuddy/` 下任何历史评估的结论、评分或优先级判断**。

## 一、结论先行

WE3D 是一个**技术野心与工程纪律都明显高于其版本号（0.0.3）的早期引擎**：渲染能力广度在纯 TypeScript WebGPU 引擎中相当少见（前向/延迟双管线、56bit GBuffer、三套大气、体积云、体渲染、IBL+SH、PCSS、1024 光源），且已建立"单测 + 真实 device 浏览器测试 + GPU 截图基线 e2e + 质量棘轮 + 导出校验 + 文档生成"的完整本地门禁闭环。最近两个星期的高强度提交集中在 glTF 解析层迁移收尾与 GPU 资源管理器重写，说明项目处于**活跃开发期而非停滞期**。

但项目距离"可对外承诺的稳定库"仍有明显距离，核心矛盾有三条：

1. **能力声明与落地程度不匹配**：README 的"进行中/规划中"标注是诚实的，但物理引擎几乎为空壳（4 文件约 3 KB）、BVH/CPU 拾取为空实现、粒子系统处于起步、编辑器完全不在仓库内；这些仍是路线图而非产品。
2. **公共 API 边界名不副实**：`src/we/index.ts` 被约定为"唯一公开入口"，实测只导出 256 个符号，而 `src/we` 实际有 666 个导出，**410 个（约 62%）未进 barrel**，`check:exports` 只告警不阻断。所谓"唯一边界"目前是软约定。
3. **质量门禁是"冻结"而非"收敛"**：`check:quality` 与基线逐项持平（104 处显式 `any`、966 行注释代码、3 个备份命名文件），没有下降趋势；e2e 基线缺失会自动生成、1 个用例长期 `skip`、部分目录 console error 降级为告警，回归防线存在可穿透的缺口。

综合判断：**架构与能力 4/5，工程化 4/5，完成度与产品化 2.5/5，整体约 3.3/5（66/100）**。适合定位为"技术演示与早期采用者引擎"，尚不适合作为生产环境依赖。

## 四、工程化与质量门禁（实测结果）

`npm run ci:no-e2e` 于 2026-11-18 实测**全绿**，逐项如下：

| 门禁 | 结果 | 关键数值 |
| --- | --- | --- |
| `lint` | 通过 | 范围仅 `src/we` |
| `format:check` | 通过 | Prettier 范围经 `.prettierignore` 收窄 |
| `check:quality` | 通过（与基线持平） | 显式 `any` 104、`@ts-ignore` 0、>1000 行文件 0、空占位 0、备份命名 3、注释代码 966 行 |
| `typecheck` | 通过 | `tsc --noEmit` |
| `test:run` | 通过 | 16 文件 / 164 用例 |
| `test:browser` | 通过 | 6 文件 / 76 用例，真实 Chromium device，含 glTF 契约 66 项 |
| `check:exports` | 通过但告警 | 256/666 符号入 barrel，410 未纳入 |
| `build:lib` | 通过 | 785.46 kB，dts 生成 2.15s |

**值得肯定**：浏览器测试不是摆设——`gltfTransformContract.browser.test.ts` 实测 66 项，覆盖资产解析、GPU bundle 读回、Draco Worker 预解码；Draco/KTX2 等 spike 测试直接验证解码器链路。`ci.yml` 与本地脚本一一对应。

**需要警惕的门禁弱点**：

1. **`check:quality` 是棘轮，不是收紧器**。当前六项指标与 2026-11-17 基线完全一致（`scripts/code-quality-baseline.json`），意味着"不恶化即通过"，104 处 `any` 与 966 行注释代码被长期合法化；其中 `src/we/model/gltf/gltf.ts` 独占 31 处 `any`。
2. **`check:exports` 只校验"已写入的 re-export 是否真实存在"**，对 410 个漏网导出仅告警。barrel 的实际覆盖率仅约 38%，"唯一公共 API 入口"是方向而非现状。
3. **无覆盖率阈值**：`vitest.config.ts` 只声明 provider 与 include，整个仓库没有 coverage 基线或产物。164+76 个用例的通过率不能回答"覆盖了多少代码"。
4. **e2e 三处可穿透缺口**（`tests/e2e/examples.spec.ts`）：
   - `:105-107` 基线 PNG 缺失时**自动生成**而非失败——首次运行或误删基线会静默"通过"；
   - `:67-68` `resourcesGPU/b4_compute_cache` 长期 `test.skip`；
   - `:92-100` `resourcesGPU` 整个目录的 console error 降级为告警，只靠截图判据。
5. **并发稳定性是已知问题**：`playwright.config.ts:24-29` 明确把 workers 从 8 固化为 4，注释写明"真实 GPU 硬件渲染下 8 workers 会偶发页面加载超时"，`CI` 下 `retries:2`。这与 `AGENTS.md` 仍写的"8 workers、与云端一致"存在**文档漂移**；多次提交记录也显示 8 workers 下有既有的 shadow/PBR 用例波动。
6. **云端不跑 e2e**：`ci.yml` 只跑 `ci:no-e2e`，视觉回归完全依赖开发机本地 `npm run ci` 的纪律。一旦有人只跑云端等价命令就提交，渲染回归不会被自动拦截。

## 六、产品化与生态缺口

1. **双包声明不一致**：README 同时宣传 `we3d` 与 `webgpu-we3d`（`:25-38`），但本仓 `package.json` 只有 `we3d`，无第二包的发布配置或构建脚本。对 npm 使用者构成直接困惑。
2. **无根 LICENSE / CHANGELOG**：根目录无项目许可证文件，`package.json.files` 也不包含 LICENSE；npm 包只带 draco/basis 的第三方 LICENSE。法律与版本可追溯性均不完整。
3. **无 tag，发布链路未闭环**：`git tag` 为空，`release.yml` 的 `v*` 触发条件从未在本地验证；`publish:if-new` 脚本存在但无任何 workflow 调用，当前为人工 2FA 发布。
4. **文档漂移**：`AGENTS.md` §三.1 描述的 `ci:no-e2e` 组成与 `package.json:49` 实际脚本不一致（实际多了 `format:check`、`test:browser`）；§三.3 写"8 workers"，配置为 4。`design/issues/vite7-lib-minify-inactive.md` 仍留"未提交 git"旧注，而问题已修复。
5. **仓库根散落本地日志**：`devserver.log`、`eslint.log`、`tsc.log`、`tsc2.log`、`fix-unused.log`、`install*.log`、`examples-console-report.json` 等 8 个文件（未被 git 跟踪，属本地 ignored 残留）。不影响发布，但干扰仓库观感。
6. **示例/演示生态仍为 doing**：README 中 `example`、`demo` 仓库标 doing，编辑器与服务端能力标 todo。作为早期引擎可接受，但限制了外部采用门槛。

## 八、优先级路线图

### P0 — 让"门禁"和"对外承诺"可信（阻塞生产采用）

1. **e2e 基线硬失败化**：基线缺失时报错而非自动生成；把 `b4_compute_cache` 的 skip 转为带明确解除条件的 ticket；`resourcesGPU` 的 console error 恢复硬断言或逐例白名单。
2. **公共 API 边界收口**：对 410 个未纳管导出做一次分类——核心类型补入 barrel / 明确标为内部（`internal` 约定或路径隔离）；`check:exports` 从"告警"升级为对新增漂移"阻断"，并建立导出快照基线。
3. **产品化三件套**：确定 `webgpu-we3d` 是否保留（保留则补构建与发布配置，否则删 README 声明）；补根 `LICENSE` 与 `CHANGELOG`；打首个 `v0.0.3` tag 验证 `release.yml`。
4. **文档与现实对齐**：修正 `AGENTS.md` 的 e2e workers（8→4）与 `ci:no-e2e` 组成描述，清理过期 issue 注记。

### P1 — 质量收敛（投入产出比最高，建议 5–8 人日）

5. **棘轮下调**：把 104 处 `any` 按模块分批清零（优先 `gltf.ts` 31 处），966 行注释代码按"死实现删除 / 有价值说明转为文档"二分；每轮同步收紧 `code-quality-baseline.json`，禁止只冻结不放宽。
6. **覆盖率门槛**：为 `vitest.config.ts` 设 thresholds 并提交覆盖率基线，优先覆盖 `command`/`scene`/`gltf` 三条主路径。
7. **死代码与命名债清理**：删除 `unuse.FXAA...wgsl` 等未引用资源、空占位方法与 39–433 B 的桩文件；评估 `commmandType` 重命名的收益与兼容成本。
8. **e2e 并发稳定性**：记录 4 workers 下的超时根因；在 CI 中固化可复现口径，消除对 `retries:2` 的隐性依赖。

### P2 — 补齐"引擎"叙事的短板（持续）

9. 物理引擎：rapier 封装从 3 KB 占位推进到刚体/碰撞体可用闭环，并配 e2e。
10. BVH / CPU 拾取：补齐三个空方法，使 README 的 `(todo)` 可摘除。
11. 粒子系统从 `BaseParticle` 推进到可渲染的最小闭环；OBJ/FBX 载入择一先落地。
12. 面积光 / 物理透明 / A-Buffer / TAA / AO-GI 系列按现有路线图推进，每项是独立的渲染管线变更，必须同步 GPU 基线。

### P3 — 生态

13. `example` / `demo` 仓库落地，提供最小可复制模板；评估 tag 后的自动化发布（待 npm 2FA 流程稳定）。
14. PR CI 引入文档新鲜度检查；清理本地 fork 目录与日志残留，补齐 golden 快照留档承诺。

## 九、一句话总结

WE3D 的**底层架构和渲染能力已经具备差异化竞争力，工程门禁在同类早期项目中属上乘**；当前真正的短板不在"会不会写引擎"，而在**公共 API 边界、质量债收敛、产品化配套与路线图兑现率**——先让门禁变成硬约束、让 README 与仓库状态一致，再谈 v0.1.0。
