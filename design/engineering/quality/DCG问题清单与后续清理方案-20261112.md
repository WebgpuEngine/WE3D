## 四、P0 详述

### P0-1 · pipeline 缓存 key 维度缺失（最优先）

**位置**：`DrawCommandGenerator.ts` → `initPipeLine()`，`cacheFlag` 数组与 `nameOfCacheFlag`。

```ts
        cacheFlag = [
            vertex.name,
            fragment.name,
            //primitive
            values.render.primitive?.topology as string,
            values.render.primitive?.cullMode as string,
            values.render.primitive?.stripIndexFormat as string,
            values.render.primitive?.frontFace as string,
            depthStencilFlag,
            multisampleFlag,
        ];
        const nameOfCacheFlag = cacheFlag.toString();
        if (this.resources.pipeline.has(nameOfCacheFlag)) {
            return this.resources.pipeline.get(nameOfCacheFlag)!;
        }
```

第 2 期已修过「depthStencil / multisample 字面量误命中同一缓存」，但 key 仍**不含**：

| 缺失维度 | 依据 | 后果 |
| --- | --- | --- |
| `DC_bindGroupLayouts` → `pipelineLayout` | `initPipeLine` 的 `descriptor.layout` 由它 `createPipelineLayout` 得到 | 命中缓存会拿到绑定**旧 layout** 的 pipeline，而 `DC_bindGroups` 按新 layout 创建，WebGPU 校验失败 |
| `fragment.targets`（format / blend） | `initShaderModule` 组装 `targets`，`initPipeLine` 放进 `descriptor.fragment` | 相同 shader、不同 blend 的 DC 误命中 |
| `vertex.buffers` = `DC_verticesBufferLayout` | `initShaderModule` 的 `GPUVertexState.buffers` | 顶点布局不同但 VS code 相同（尤其 NDC 模式跳过反射）时误命中 |
| `entryPoint` / `constants` | `GPUVertexState` / `GPUFragmentState` 的字段 | 不同常量覆盖误命中 |

**另有两个 key 质量问题**：
1. `cacheFlag.toString()` 用逗号拼接，而 `depthStencilFlag` / `multisampleFlag` 是 `stableStringify` 的 **JSON 字符串、本身含逗号**；`undefined` 项又变空串 → key 不是单射，且无法从 key 反推状态。建议 `JSON.stringify(cacheFlag)`（或用 `\u0000` 之类不可能出现在值里的分隔符）。
2. `createPipelineLayout()` 在**查缓存之前**无条件执行，命中时白建一个 `GPUPipelineLayout`；应移到未命中分支。

**建议修法**：把「构造 descriptor」与「计算 key」合并为「对最终 descriptor 的稳定序列化」——`descriptor` 里除 GPU 对象引用外的可序列化部分（含 `layout` 对应的 layout 列表标识、`fragment.targets`、`vertex.buffers`、`constants`、`primitive`、`depthStencil`、`multisample`）整体走 `stableStringify`。这样天然不漏维度，且 `stableStringify` 已在本仓库验证过（键排序、内容相同则 key 相同）。

**验收**：§二 第 3 项 key 快照测绿 + 新增「仅 layout / 仅 targets / 仅 vertex.buffers 不同 → 不复用」三组断言 + `npm run ci` e2e 85/85 零差值 + `test:browser` 73/73。

**风险**：改 key 会让缓存命中率短期下降（首次多建 pipeline），属预期；不要为了「命中率」把维度砍回去。

### P0-2 · `targets` 原地修改污染调用方

**位置**：`DrawCommandGenerator.ts` → `initShaderModule()`。

```ts
            if (values.render.fragment.targets) {
                targets = values.render.fragment.targets; //使用传入参数
            }
            ...
            if (values.transparent) {
                for (let i = 0; i < values.transparent.length; i++) {
                    targets[i].blend = values.transparent[i];
                }
            }
```

**证据**：默认路径的 `getColorAttachmentTargetsOfForward/Blend/MSAA/MSAAinfo`（`src/we/core/gbuffers/base.ts` L274–307）每次都新建数组，所以默认路径安全；但**传入 `targets` 的路径**直接持有调用方对象引用并写入 `blend`。若调用方复用同一个 targets 数组（材质常量、多 DC 共享），blend 状态会串到别的 DC，且是跨帧累积型污染。

**建议修法**：`targets = values.render.fragment.targets.map(t => ({ ...t }))`（注意 `blend` 若本身是对象且被写，按需浅/深拷贝一层）。同时给 `values.transparent.length > targets.length` 加越界保护——当前 `targets[i]` 可能 `undefined` 而抛错。

**验收**：新增「传入同一 targets 数组、两次不同 transparent → 两次 descriptor 的 blend 互不影响」断言；e2e 零差值。

---

### P0-3 · `resources.pipeline` 无淘汰/失效机制

**位置**：`src/we/core/resources/resourcesGPU.ts` L90 `pipeline: Map<string, GPURenderPipeline>`；`check()`（L433–448）在 L405–425 被调用时**未包含 `this.pipeline`**（同 `shaderModuleOfString` 有 check，pipeline 没有）。

**影响**：pipeline key 由 shader md5 + 状态组合而成，运行期新增材质/状态会持续建新 pipeline，Map 无界增长且持有 GPU 对象；`check()` 只清理 `undefined` / `_isDestroy` 项，对「长期不再使用但仍有效」的 pipeline 无效。

**建议修法**（需结合 P0-1 一起设计）：
- 明确缓存生命周期：按 scene 生命周期持有，还是加 LRU/引用计数；
- 至少把 `this.check(this.pipeline)` 纳入现有清理流程，并在 key 里带上 layout 版本（如 `scene.IBL` 变化、shadowmap 重建时应失效）；
- 参考 `Scene.refreshSystemBindGroupAndBindGroupLayoutZeroForCamera()` 的重建思路。

**验收**：长运行场景（反复增删实体/材质）下 pipeline 数量有上界；`npm run ci` + `test:browser` 全绿。

## 五、P1 详述

### P1-1 · 恒不可达分支

**位置**：`DrawCommandGenerator.ts` → `generateDrawCommand()` 的 `if (values.system) { ... } else { const renderPassDescriptor = () => { ... } }`。

`else` 是 `values.system` 为假的分支，其内部 `else if (this.scene.finalTarget.NDC == true && values.system?.MSAA)` 中 `values.system?.MSAA` **恒为 `undefined`**，永不进入；且该分支与末尾默认分支都返回 `this.scene.getRenderPassDescriptorForNDC()`，行为无害但误导。闭包在 DC 执行时才求值，除非外部事后修改 `values` 对象，否则可判死。

**建议修法**：删除该 `else if`，把闭包里的大段注释掉的旧 RPD 逻辑一并清理；`let renderPassDescriptor` 未初始化 + `return renderPassDescriptor!` 可改为各分支直接 `return`，去掉非空断言。

**风险**：低（不改变任何当前可达路径的输出）。建议与 P2-3 一起做。

### P1-2 · `inputDC` 只 push 不消费

**位置**：`DrawCommandGenerator.ts` L63 `inputDC: IV_DC[] = []`、L82 `this.inputDC.push(values)`。

**证据**：全仓检索只有 `DrawCommandGenerator.test.ts` L273 的 `expect(generator.inputDC).toEqual([values])` 读它，无任何业务消费或清理。注释写「保存每个 DC 的 init 参数，为了后续的更新 uniform 使用（如果其中有 update 选项）」，但该能力未实现。每个元素持有完整 `IV_DC`（shader code、GPUBuffer 引用），动态增删实体场景持续累积。

**决策点（需人工确认）**：这是「预留但没实现」还是「已废弃」？
- 若预留：补上 `update` 消费逻辑 + 清理策略（DC 销毁时移除），并加测试；
- 若废弃：删除字段与 push，同步改 C0 测试的 `expect(generator.inputDC)` 断言。

> 注意：删除会动到 C0 特征测试，按 [C0特征测试使用说明](./C0特征测试使用说明.md) §四属于「有意变更」，需在 commit message 说明。

### P1-3 · `initVertexPart` 的 5 组重复分支（方案已登记）

**位置**：`src/we/core/command/drawCommandGenerator.vertex.ts`，`for (const key in values.data.vertices)` 内约 L62 / L137 / L226 / L450 / L506 五组分支（分别处理 `Array.isArray(number[])`、另一数组形态、`ArrayBuffer.isView`、`isI_vsAttributeMerge`、`isVSGPUBufferBundle`）。

每组都在重复同一套动作：`switch (lowKey)` 决定 `arrayStride` / `format` / `viewType` → `scope.getWgslValueFormat()` → `scope.formatLocationStringOfAttribute()` → 查/建 `vertexPointers[lowKey]` 缓存 → `createPointer` → 构造 `_GPUVertexBufferLayout`。`pointerParams` 构造在 L189 / L306 / L415 / L472 / L596 等处重复 5 次，`vertexPointers[lowKey] = ...` 在 L116 / L204 / L317 / L426 / L483 / L508 重复 6 次。

**这正是方案 §四 C8 写明的「优先拆 635 行重复结构」目标**，C8 为保证等价搬移刻意逐字保留、未重构。

**建议修法**：
1. 抽 `resolveVertexAttribute(lowKey): { arrayStride, format, viewType, wgslFormat }` 静态表（把 5 份 `switch` 合成 1 份查表）；
2. 抽 `getOrCreateVertexPointer(scope, values, lowKey, params)` 统一缓存读写；
3. 5 组分支只保留各自真正不同的部分（数据来源、byteSize 计算、dynamic 处理）。

**风险**：**高**。5 组分支的 `byteSize`、`viewType`、是否传 `values.system?.parent` 给 `createPointer`、dynamic 顶点处理都有细微差异，且 C0 未覆盖该函数的返回结构。必须先完成 §二 第 1 项特征测试，再逐组替换、每组一次验证。

### P1-4 · `initUniformPart` 的 `layoutNumber`

**位置**：`DrawCommandGenerator.ts` → `initUniformPart()` L262–337。

`let layoutNumber = 0` 在 system 分支被反复赋值 0→1→2→3，槽位靠魔法数字隐式约定（0=system0、1=entity、2=material、3=IBL）；L312 无条件 `layoutNumber = 3`；而 uniforms 分支（L330+）又把同名变量当作「已处理组数」用于 `if (layoutNumber > 3)` 上限判断与 label 生成，两种语义混用。

另有 `new Array(4).fill(undefined)` 作为 `GPUBindGroupLayout[]` 传给 `createPipelineLayout`（含 `undefined` 槽位），语义依赖 WebGPU 对 nullable 的容忍，值得显式化。

**建议修法**：定义 `const SLOT = { system: 0, entity: 1, material: 2, ibl: 3 } as const`；uniforms 分支另用 `groupCount` 计数；把 `undefined` 槽位显式写成 `null`（若确认 WebGPU 允许）或补齐空 layout。

**风险**：中。涉及 bindGroup 槽位，改动前需 §二 第 2 项快照。

### P2-2 · `formatLocationStringOfAttribute` 的 `values` 参数未使用

`wgslVertexFormat.ts` 的该函数签名为 `(values: IV_DC, location, name, format)`，但 `values` 只在**注释掉的** `@interpolate` 旧实现里出现，函数体完全没用。

**建议修法**：去掉 `values` 形参，同步 4 处调用与委托壳；`@location` 输出快照不变。若未来要恢复 `@interpolate`，再按需加回。
