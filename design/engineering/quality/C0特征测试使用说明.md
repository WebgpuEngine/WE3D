# C0 前置特征测试 · 使用与维护说明

> 配套：[巨型文件拆分落地方案-20261111](./巨型文件拆分落地方案-20261111.md)。本文档供后期维护者使用，说明 C0（第 3 期拆分前建立的行为特征基线）**测了什么、怎么跑、怎么改**。

## 一、背景与定位

第 3 期对 8 个巨型文件（>1000 行）做「等价搬移」拆分前，必须先有一张**行为快照**，否则拆完后无法证明「没改行为」。C0 用三个特征测试（characterization test）把当前帧循环 / 渲染队列 / 命令生成的关键行为录成快照：

- 它们不是「断言式单测」（验证正确性），而是「变更探测器」（当前行为 = 正确，偏离即报警）。
- 测试**完全在 node 环境运行**，用 spy / stub 替换 GPU 依赖，不碰真实渲染、不碰 `test:baseline` 的 GPU 截图基线。
- 测试文件（`*.test.ts`）**不计入** `check-code-quality` 的 ratchet 指标（`explicitAny` / `giantFiles` 等只统计 `src/we` 下的生产 `*.ts`）。因此改这些测试不会影响质量基线，但需要人工评审。

## 二、工作原理：测了哪些文件的哪个部分

### 2.1 `scene.test.ts` → `Scene.update()` 的帧更新顺序

- **被测对象**：`src/we/core/scene/scene.ts` 的 `Scene.update()`。
- **机制**：构造一个真实 `Scene` 实例，用 spy stub 覆盖 13 个 manager 的 `update` 及 `generateBox/generateSphere/updateBVH`，把每次调用名 push 进 `calls` 数组，再比对 `calls` 与预期序列。
- **三个用例**：
  1. **调用序列快照**（`EXPECTED_ORDER`，17 项）：`onUpdate` → 13 个 manager → `generateBox` → `generateSphere` → `updateBVH`，逐项相等。
  2. **隐式依赖顺序**：用 `indexOf` 断言动画先于 `entity`、BPC 先于内存块、相机先于后处理等——这些顺序在源码里是隐式的（没有依赖声明），是回归高危区。
  3. **事件值**：`update()` 首步抛出的自定义事件固定为 `eventOfScene.onUpdate`。
- **为什么能发现回归**：C6 把 `scene.ts` 拆成子模块时，只要 `update()` 的调用顺序被改动，用例 1 立即红。

### 2.2 `renderManager.test.ts` → `RenderManager` 阶段枚举与命令队列结构

- **被测对象**：`src/we/core/scene/renderManager.ts` 的 `E_renderPassName` 枚举、`RC` 渲染命令队列键集合、`listCommandType` 引用、`push()` 分类逻辑。
- **机制**：用 mock `scene` 构造真实 `RenderManager`，断言枚举 / 键 / 分类，不触发真实渲染。
- **用例**：
  1. **枚举值 + 声明顺序**（`EXPECTED_ENUM_VALUES`，21 项）：覆盖 `Object.values(E_renderPassName)` 的值与顺序。
  2. **RC 键集合**（`EXPECTED_RC_KEYS`，18 项）：覆盖 `Object.keys(manager.RC)`。
  3. **`listCommandType` 引用**：断言前四通道（opaque / transparent / background / transmission）的引用未被 `push` 替换。
  4. **`push()` 分类**：数组 / 双层 `Map` / 距离队列三类各一组，验证分类正确。
  5. **异常路径**：缺参与非法 `kind` 抛错。
- **为什么能发现回归**：C3 抽 `E_renderPassName` 全枚举与 5 个接口时，re-export 写错或枚举值/顺序变动会立即暴露。

### 2.3 `DrawCommandGenerator.test.ts` → 生成结果

- **被测对象**：`src/we/core/command/DrawCommandGenerator.ts` 的 `getWgslValueFormat` / `formatLocationStringOfAttribute` / `generateDrawCommand`。
- **机制**：stub 四个 `init*` 方法记录调用顺序，断言输入透传与输出结构。
- **用例**：
  1. **WGSL 格式映射表快照**（`WGSL_FORMAT_TABLE`，35 项）：逐键断言，并断言未知格式抛 `'顶点属性格式不能匹配数据'`。
  2. **`@location` 字符串输出快照**：含尾随逗号与空格（如 `'@location(3) position : vec3f ,'`），防止字符串拼接被无意识改动。
  3. **`generateDrawCommand` 编排顺序**：`initVertexPart → initUniformPart → initShaderModule → initPipeLine` 四步顺序，以及中间结果（`DC_vertexNames` / `DC_localtions` / `DC_verticesBufferLayout` / `DC_bindGroupLayouts`）如何逐层透传。
- **为什么能发现回归**：C8 抽 WGSL 格式表 / `stableStringify` / `initVertexPart` 时，映射表或编排顺序任何字节级变化都会报警（pipeline 缓存 key 依赖这些）。

### 2.4 已知覆盖缺口（诚实记录，后期补）

- **`RenderManager.render()` 的 9 阶段执行序列**（compute → shadowmapOpaque → forward → MSAA → defer → afterDeferRender → transparent → toneMapping → postprocess）**目前无断言**。C3 只抽枚举与接口、不碰 `render()` 方法体，因此够用；但若要改 `render()` 顺序，现有测试不会报警——须先补 2.1/2.2 缺口。
- **`scene.ts` 的 RPD / bindGroup0 构造顺序**未断言（C6 拆分时建议补）。

## 三、使用方法

### 3.1 运行

```bash
# 全量门禁（含 e2e 85 例）
npm run ci

# 仅 node 单测（含这三个测试）
npm run test:run

# 单文件
npx vitest run src/we/core/scene/scene.test.ts
npx vitest run src/we/core/scene/renderManager.test.ts
npx vitest run src/we/core/command/DrawCommandGenerator.test.ts

# 浏览器测试（含 glTF 契约 66 项）
npm run test:browser
```

### 3.2 环境

- 纯 node，无需 GPU。`Scene.update()` 用 spy stub 注入；`RenderManager` / `DrawCommandGenerator` 用 mock `scene` 构造。
- **自动提醒**：若 `Scene.update()` 里新增了一个 manager 但没在测试里 stub，`this.xxx.update is not a function` 会直接抛错，测试即失败（不会静默漏测）。

### 3.3 读失败信号

- **红色 = 当前行为与快照不符**。第一反应是「这是回归还是有意变更？」——不要无脑改测试让绿。
- 若是拆分类重构（C1–C8）导致红：说明拆分**改变了行为**，是缺陷，应修拆分而不是改测试（见 §四.1）。
- 若是有意功能演进导致红：按 §四.2 同步改测试，并在 commit message 里说明顺序变更的意图。

## 四、变更方式（重点）

### 4.1 拆分类重构（C1–C8）：不要改这些测试

- 拆分提交里 `*.test.ts` 应当**零改动**（git diff 不含这些文件）。
- 若拆分后测试变红，说明搬移改变了行为 = 缺陷，回滚或修正拆分，绝不用改测试掩盖。
- 这也是「测试文件在 diff 里零改动」能作为行为等价证据的原因。

### 4.2 功能演进：必须同步改测试

#### 新增一个 manager 到 `Scene.update()`

改 `scene.test.ts` 共 **3 处**：

1. `EXPECTED_ORDER` 数组（约 L79）加一项；
2. `makeUpdateSpyScene` 的 stub 列表（约 L114）加 `xxxManager: manager('xxxManager')`；
3. 第三个用例里的 `Object.assign(scene, { ... })` 手写 stub 列表（约 L173）加一项。

> 注意：清单 2 与清单 3 是重复的（历史遗留），新增时容易漏一处。漏了会导致用例 3 里 `this.xxx.update` 未定义而失败，排查成本高。建议后续重构为「从 `EXPECTED_ORDER` 派生 stub」，见 §五。
> 若新 manager 有依赖约束，在隐式顺序用例补一条 `indexOf` 断言。

#### 新增一个 render 阶段到 `RenderManager`

改 `renderManager.test.ts`：

1. `EXPECTED_ENUM_VALUES`（约 L39）若新增枚举项则补；
2. `EXPECTED_RC_KEYS`（约 L63）若新增 `RC` 队列则补；
3. `kinds` 数组（约 L108）+ `push` 分类用例补对应分支；
4. **`render()` 阶段执行序列目前无断言（§2.4 缺口）**，新增阶段不会触发报警——须先补该缺口再改顺序。

#### 更改 DCG 顶点格式映射 / 生成编排

改 `DrawCommandGenerator.test.ts`：

1. `WGSL_FORMAT_TABLE`（35 项）随映射表增删；
2. `generateDrawCommand` 用例里的 `calls` 数组随编排四步顺序变化。

### 4.3 维护约定

- 这些测试**不计入** `check-code-quality` 的 ratchet（`*.test.ts` 被排除在生产统计外）。
- 不跑 `test:baseline`（GPU 截图基线不动）；拆分不改变行为，e2e 85 例逐帧差值出现即判缺陷。
- 删除需谨慎：第 3 期拆分结束并评估后，再决定是把顺序断言长期保留（守护隐式依赖图）还是降级为宽松契约。
