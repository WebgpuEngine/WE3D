## 一、结论先行

1. **06 的判断在「没有专项治理」这一层是准确的，但容易被误读成「存量一点没动」。** 01 给代码质量 ★★☆☆☆，05、06 均维持 ★★☆☆☆，确实没有任何以「降 `any` / 拆巨型文件 / 清死代码」为目标的批次；但 glTF 迁移顺带偿还了一部分存量（详见 §2.4）。
2. **真正缺的是治理闭环，不是一次大扫除**：没有量化指标、没有门禁、没有「只降不升」的约束，所以任何一次性清理都会回退。`format` 正是现成反例——2026-10-30 已格式化 290 文件并单独提交（`0a1468d`），但 `format:check` 未接入 CI，2026-11-11 实测又有 **66 个文件不合规**（迁移后新增的 `e2e-cases/gltf/` 用例、新解析层文件与工作区增量改动）。
3. **因此第一期不动任何渲染代码**：先建立 ratchet 门禁与质量基线（本期已落地），后续每期只允许指标下降，且每期都跑 `npm run ci:no-e2e`（涉及渲染时按 AGENTS §三.1 补 `test:baseline` + `npm run ci`）。这直接兑现 06 §六 的路径依赖提醒——「先有基线，再动代码」。

## 三、根因分析（为什么 5 个月没动）

1. **无度量、无门禁**：`any` / 文件长度 / 死代码都没有可复现的数字，也没有「不许上升」的约束；`eslint.config.js` 甚至主动关闭了两条相关规则。改进无法验收，退化无法拦截。
2. **一次性清理会回退**：`format` 是最直接的反例（1030 全绿 → 1111 66 文件漂移）。没有 ratchet，任何「大扫除」都只是瞬时状态。
3. **巨型文件位于渲染主路径且缺特征测试**：`Scene.update()` 顺序、`RenderManager` 阶段顺序、`DCG` 的 vertex/uniform 生成都没有行为级断言，只有截图间接覆盖；谁也不敢先动。
4. **类型缺口在抽象层**：`ModelDataLoader` 的 16 个 `any` 签名把松散类型传染给 `gltf.ts` 与 `resourcesGPU.ts`，只改局部收效甚微，必须从契约层一次收口。
5. **死代码判定缺「引用 + 用途」双确认**：`*.copy.gltf` 是验证资产、空类骨架可能是未来扩展点；按文件名批量删会误伤，导致清理被无限期搁置。

## 四、治理原则与分期方案

**原则**

- **先度量后动手**：任何清理前先有 ratchet 基线；指标只降不升，基线只能显式更新并随治理同一次提交。
- **不改变可观察行为**：本期与后续各期均不改渲染顺序、shader 内容、公共 API；`e2e` 截图基线不动（若有任何视觉变化，按 AGENTS §三.1 走 `test:baseline` + `npm run ci`）。
- **小步提交**：每期单独 commit（格式 `MMDD 具体内容`），失败可单步回滚。
- **公共 API 零漂移**：`src/we/index.ts` 是唯一边界，每期 `check:exports` 必过。
- **数据资产与测试资产不误删**：按 §2.5 的 A–E 分类决策。

### 第 0 期 · 建立度量与门禁（**2026-11-11 已完成**，本次交付）

- 新增 `scripts/check-code-quality.mjs`：统计 6 项指标，与 `scripts/code-quality-baseline.json` 比较，任一指标上升即非 0 退出；下降时提示用 `npm run quality:baseline` 收紧（**不自动放宽基线**）。
- `package.json` 新增 `check:quality` / `quality:baseline`，接入 `ci`、`ci:no-e2e`、`prepublishOnly`；云端 `ci.yml` 调用 `ci:no-e2e`，自动同步，无需改 workflow。
- 清理 A 类 6 个无引用空占位 `.ts`（`emptyStubFiles`: 6 → 0）。
- 验收：`npm run ci:no-e2e` 全绿（详见 §五）。

### 第 1 期 · 低成本 `any`（1～2 d，零渲染风险）

| 动作 | 目标 |
| --- | --- |
| 4 处生效 `@ts-ignore` 逐处补类型 / 断言，消除硬逃逸 | `typeEscapes` 4 → 0 |
| `baseTexture.ts:106` 的 `undefined as any` 改为可选字段类型；`BaseAnimation.ts:113` 的 `this as any` 改为接口约束 | 生产 `as any` → 0 |
| `scene.ts:1427` `getEntityByID(): any` 跟随 `getByID(): T \| undefined` | 公共 API 类型化但签名兼容 |
| 32 处测试 mock `as any` 改 `Partial<T>` / `satisfies` / 类型化 `globalThis` | 测试不再示范坏写法 |
| 内部局部变量 / 工具函数中的 `any`（`coreFunction.ts`、`command/baseFunction.ts`、`command/base.ts` 等） | `explicitAny` 230 → ≤ 190 |

每消除一批即 `npm run quality:baseline` 收紧，并跑 `npm run ci:no-e2e`。

### 第 2 期 · 结构性 `any` + 死代码（3～5 d）

1. **契约层**：用现有 `GLTF.I*` 收窄 `ModelDataLoader` 16 个签名，级联修正 `gltf.ts` / `gltfTransformLoaders.ts` / `resourcesGPU.ts`；`IV_Scene` 的配置项类型化（`rapier` 物理对象、`entities/materials/...` 数组）。验收：`typecheck`、`test:browser` 的 66 项 glTF 契约测试、`e2e` 零差值。
2. **死代码**：删除 6 处整段注释（§2.5 E）与 4 个 C 类备份 `.wgsl`（删前读 shader 文档）；D 类 `*.copy.gltf` 仅改名并同步 Gate 0 清单；B 类空类骨架提交人工决策。
3. 目标：`explicitAny` ≤ 120、`commentedCodeLines` ≤ 400、`backupNamedFiles` ≤ 3（仅剩改名中的资产）。

### 第 3 期 · 巨型文件拆分（5～8 d，风险最高，必须最后做）

1. **先补特征测试**（这一步不可省）：`Scene.update()` 的 manager 调用顺序与依赖、`RenderManager` 阶段枚举 → 命令队列顺序、`DCG` 的 vertex layout / uniform bindGroup / shaderModule 生成结果（快照式断言）。
2. **再按职责抽取**，保持类与公共方法签名不变，只把实现搬进同目录新模块：
   - `DrawCommandGenerator` → `vertexLayout` / `uniformPart` / `shaderModule` / `pipeline` 四块（优先拆 635 行的 `initVertexPart` 重复结构）；
   - `Scene` → 系统 bindGroup 0、RPD 描述、帧循环三部分；`update()` 的 15 步硬编码顺序改为**声明式依赖表**（执行顺序必须逐项等价，先写断言再改）；
   - `RenderManager` → 阶段注册 / 命令队列 / 各 render 分支。
3. 每拆一个文件跑一次 `npm run ci`（含 e2e 差值检测）；`check:exports` 必过，不允许公共 API 变化。
4. 目标：`giantFiles` 8 → ≤ 3，`explicitAny` ≤ 80，`commentedCodeLines` ≤ 200。

### 第 4 期 · 门禁固化（收尾，0.5 d）

- 补跑一次 `npm run format`（单独 commit）清掉 66 文件增量漂移，再把 `format:check` 接入 `ci:no-e2e`；把 `examples-console-report.json` 等生成物加入 `.prettierignore`。
- 对已清理的目录用 ESLint `overrides` 开 `@typescript-eslint/no-explicit-any: error`，实现「从 ratchet 到硬规则」的过渡；`ban-ts-comment` 同步开启。
- 评估把 `test:browser` 补进 `npm run ci`（当前仅 `ci:no-e2e` 含），消除 glTF 契约测试在默认 CI 链路的缺口。
